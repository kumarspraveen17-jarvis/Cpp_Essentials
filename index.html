Core Language Foundations & Idioms

This module fills in the foundational C++ mechanics that every other topic in this course quietly assumes you already know: the type system, casting, references, namespaces, and a handful of class-design idioms (friend, mutable, static members, initializer lists) that show up constantly in real code and in interviews.

1. Type System — bool, wchar_t, Strict Typing & auto

C++ is statically and strongly typed: every variable's type is fixed at compile time, and the compiler rejects most implicit conversions that could silently lose information. This catches entire categories of bugs before the program ever runs.

type_system.cppC++
#include <iostream>

int main() {
    // bool — exactly true or false, stored as 1 byte, but only 2 valid values
    bool isReady = true;
    std::cout << std::boolalpha << "isReady = " << isReady << "  sizeof(bool) = " << sizeof(bool) << "\n";

    // wchar_t — a "wide" character type, for representing characters beyond plain ASCII
    // (its exact size is platform-defined: typically 2 bytes on Windows, 4 on Linux)
    wchar_t letter = L'A';         // L prefix marks a wide character literal
    std::wcout << L"Wide char: " << letter << "  sizeof(wchar_t) = " << sizeof(wchar_t) << "\n";

    // Strict type checking — this would NOT compile:
    // int x = "hello";        // ERROR: cannot convert const char* to int
    // Compare to C, which is far more permissive with implicit conversions.

    // auto — the compiler deduces the type from the initializer, at COMPILE time (not dynamic typing!)
    auto count = 42;              // deduced as int
    auto price = 19.99;          // deduced as double
    auto name = std::string("Praveen");  // deduced as std::string
    std::cout << count << " " << price << " " << name << "\n";

    // count = "text";   // still a compile ERROR — auto fixes the type ONCE, at declaration;
                       // it is not a dynamically-typed variable afterward
    return 0;
}
Expected Output
isReady = true sizeof(bool) = 1 Wide char: A sizeof(wchar_t) = 4 42 19.99 Praveen
💡
Key Takeaway — auto Is Not Dynamic Typing auto only saves you from writing the type — the compiler still locks in a single, fixed, static type at the point of declaration. It's identical in strictness to writing the type explicitly; it's purely a readability/maintenance tool (especially useful for long iterator or template types).

2. Type Casting — The Four C++ Casts

C-style casts (int)x are discouraged in C++ because they silently do whichever of four very different operations happens to compile, hiding your actual intent. C++ gives you four named casts instead, each announcing exactly what kind of conversion you mean.

four_casts.cppC++
#include <iostream>

struct Base { virtual ~Base() = default; };
struct Derived : Base { void hello() { std::cout << "Derived::hello()\n"; } };

int main() {
    // 1. static_cast — compile-time-checked conversions between RELATED types
    //    (numeric conversions, up/downcasts you know are safe, void* back to a type)
    double d = 3.99;
    int i = static_cast<int>(d);          // 3 — truncates, compiler CHECKS the conversion makes sense
    std::cout << "static_cast: " << i << "\n";

    // 2. dynamic_cast — RUNTIME-CHECKED downcast in a polymorphic hierarchy;
    //    returns nullptr (for pointers) if the object isn't ACTUALLY that derived type
    Base* basePtr = new Derived();
    if (auto* d2 = dynamic_cast<Derived*>(basePtr)) {
        std::cout << "dynamic_cast succeeded: "; d2->hello();
    }
    Base justBase;    // a REAL Base, not a Derived
    if (dynamic_cast<Derived*>(&justBase) == nullptr)
        std::cout << "dynamic_cast correctly refused an unrelated object\n";

    // 3. const_cast — adds or REMOVES const/volatile — the ONLY cast that can do this
    const int readOnly = 100;
    int* mutablePtr = const_cast<int*>(&readOnly);
    std::cout << "const_cast exposed value: " << *mutablePtr << "\n";
    // *mutablePtr = 5;  // UB if the ORIGINAL object was genuinely const — legal only when
                        // the underlying object wasn't actually declared const to begin with

    // 4. reinterpret_cast — reinterprets raw bits as a DIFFERENT, UNRELATED type;
    //    no safety checks at all, the most dangerous cast, needed for low-level/hardware code
    int value = 65;
    char* bytePtr = reinterpret_cast<char*>(&value);
    std::cout << "First byte of int 65 reinterpreted as char: " << bytePtr[0] << "\n";

    delete basePtr;
    return 0;
}
Expected Output
static_cast: 3 dynamic_cast succeeded: Derived::hello() dynamic_cast correctly refused an unrelated object const_cast exposed value: 100 First byte of int 65 reinterpreted as char: A
CastChecked?Use for

🔴
Common Pitfall const_casting away const and then writing to an object that was originally declared const (not just accessed through a const reference/pointer to a non-const object) is undefined behavior — the compiler is allowed to have placed that object in read-only memory. const_cast is only safe when the underlying object is genuinely non-const, and you're just removing an overly restrictive view of it (e.g., calling a poorly-written legacy function that forgot to mark a parameter const).

3. References vs Pointers

A reference is an alias for an existing object — not a separate variable holding an address. Once bound, it can never be re-seated to refer to something else, and it can never be null.

references_vs_pointers.cppC++
#include <iostream>

// Pass-by-reference — no copy is made, and the function can modify the caller's variable
void increment(int& x) { ++x; }

// const reference — no copy AND no modification allowed. The standard way to pass
// large objects (strings, vectors, custom classes) cheaply and safely.
void printLength(const std::string& s) {
    std::cout << "Length: " << s.length() << "\n";
    // s += "x";   // COMPILE ERROR — s is const, cannot modify through it
}

int main() {
    int value = 10;
    increment(value);
    std::cout << "After increment: " << value << "\n";   // 11 — modified through the reference

    std::string longString("a fairly long string that we don't want to copy");
    printLength(longString);   // no copy made — just an alias passed in

    // Pointers CAN be null, CAN be reseated, and need explicit dereferencing
    int a = 1, b = 2;
    int* ptr = &a;
    ptr = &b;              // legal — pointer reseated to a different object
    int& ref = a;
    // ref = b;  this does NOT reseat ref — it ASSIGNS b's value into a, since ref IS a
    ref = b;
    std::cout << "a is now: " << a << " (ref never changed WHAT it refers to)\n";

    // lvalue reference: binds to a named, addressable object — int&
    // rvalue reference (C++11): binds to a temporary about to be destroyed — int&&
    // This is the foundation of move semantics covered in the OOP module's Rule of Five.
    int& lref = a;               // lvalue reference — 'a' has a name and an address
    int&& rref = 42 + 8;          // rvalue reference — binds to the temporary result 50, extending its life
    std::cout << "lref=" << lref << " rref=" << rref << "\n";
    return 0;
}
Expected Output
After increment: 11 Length: 48 a is now: 2 (ref never changed WHAT it refers to) lref=2 rref=50

4. Namespaces

A namespace groups related names (functions, classes, variables) under a common prefix, preventing collisions between identically-named things from different parts of a large codebase or third-party libraries.

namespaces.cppC++
#include <iostream>

// Defining a namespace
namespace MotorControl {
    void start() { std::cout << "MotorControl::start()\n"; }
    int maxSpeed = 100;

    // Nested namespace — groups things even more specifically
    namespace Diagnostics {
        void runSelfTest() { std::cout << "MotorControl::Diagnostics::runSelfTest()\n"; }
    }
}

// DoorControl has its OWN start() — no collision, because it's in a different namespace
namespace DoorControl {
    void start() { std::cout << "DoorControl::start()\n"; }
}

// Anonymous namespace — everything inside is only visible in THIS FILE (internal linkage).
// This is the modern C++ replacement for "static" at file scope, used to avoid polluting
// the global namespace with helper functions that other translation units should never see.
namespace {
    void internalHelper() { std::cout << "internalHelper() — private to this file\n"; }
}

int main() {
    MotorControl::start();                 // fully qualified — always unambiguous
    DoorControl::start();                  // same function name, different namespace — no clash
    MotorControl::Diagnostics::runSelfTest();

    using MotorControl::maxSpeed;      // using-declaration: bring in ONE specific name
    std::cout << "maxSpeed = " << maxSpeed << "\n";

    internalHelper();                    // callable in this file, invisible to any other .cpp file
    return 0;
}
Expected Output
MotorControl::start() DoorControl::start() MotorControl::Diagnostics::runSelfTest() maxSpeed = 100 internalHelper() — private to this file
🔴
Avoiding Namespace Pollution — Don't using namespace std; in Headers A blanket using namespace std; pulls every name from the entire std namespace into scope, defeating the entire purpose of namespaces and risking silent name collisions as the standard library grows in future C++ versions. In header files, this pollution leaks into every file that includes that header. Rule of thumb: never write using namespace at file/header scope in production code — qualify names (std::cout) or use targeted using std::cout; declarations inside a function body instead.

5. Function Enhancements

Function overloading was introduced briefly in the OOP module's compile-time polymorphism section — here are the two remaining function-level tools: default arguments and inline.

function_enhancements.cppC++
#include <iostream>

// Default arguments — callers can omit trailing parameters
void connect(std::string host, int port = 8080, bool useTLS = true) {
    std::cout << "Connecting to " << host << ":" << port
              << (useTLS ? " (TLS)\n" : " (plain)\n");
}

// inline — a HINT to the compiler to substitute the function body directly at the call
// site instead of generating a call, eliminating call overhead for small, hot functions
inline int square(int x) { return x * x; }

// The OLD way — a preprocessor macro. Looks similar, behaves VERY differently.
#define SQUARE_MACRO(x) ((x) * (x))

int main() {
    connect("lift-controller.local");                  // uses BOTH defaults: port 8080, TLS true
    connect("lift-controller.local", 9090);           // overrides port only
    connect("lift-controller.local", 9090, false);   // overrides both

    std::cout << "square(5) = " << square(5) << "\n";

    // The classic macro bug inline functions don't have — side effects evaluated multiple times
    int i = 5;
    std::cout << "SQUARE_MACRO(i++) = " << SQUARE_MACRO(i++) << "  (i is now " << i << ")\n";
    // The macro expands to ((i++) * (i++)) — i is incremented TWICE, and the result is
    // garbage/undefined order of evaluation. square(i++) would increment i exactly ONCE,
    // as expected, because it's a real function call with real parameter evaluation rules.
    return 0;
}

6. Dynamic Memory — Alignment & std::bad_alloc

The Pointers module covered new/delete/new[]/delete[] fully. Two things weren't covered there: what happens when allocation fails, and how to control memory alignment for hardware or performance requirements.

bad_alloc_and_alignment.cppC++
#include <iostream>
#include <new>

struct alignas(16) Vec4 {   // force 16-byte alignment — common requirement for SIMD instructions
    float x, y, z, w;
};

int main() {
    // std::bad_alloc — thrown by 'new' when the heap genuinely cannot satisfy the request
    try {
        size_t hugeSize = static_cast<size_t>(-1);   // an absurdly huge, impossible-to-satisfy size
        int* arr = new int[hugeSize];
        delete[] arr;
    } catch (const std::bad_alloc& e) {
        std::cout << "Caught bad_alloc: " << e.what() << "\n";
    }

    // nothrow new — returns nullptr instead of throwing, useful when exceptions are disabled
    int* p = new(std::nothrow) int[static_cast<size_t>(-1)];
    std::cout << "nothrow new result: " << (p ? "allocated" : "nullptr (as expected)") << "\n";

    // Memory alignment
    std::cout << "alignof(Vec4) = " << alignof(Vec4) << " bytes\n";
    Vec4 v;
    std::cout << "address of v is 16-byte aligned: " << std::boolalpha
              << (reinterpret_cast<uintptr_t>(&v) % 16 == 0) << "\n";
    return 0;
}
Expected Output
Caught bad_alloc: std::bad_alloc nothrow new result: nullptr (as expected) alignof(Vec4) = 16 bytes address of v is 16-byte aligned: true
⚠️
Why Alignment Matters for CPU/Embedded Work Many hardware peripherals (DMA controllers, SIMD instructions) require data to start at an address that's a multiple of a specific power of two — misaligned access can silently degrade performance or, on some architectures, cause a hard fault. alignas lets you declare that requirement directly on a type instead of relying on luck.

7. The this Pointer, const Correctness & mutable

Every non-static member function secretly receives a hidden parameter: this, a pointer to the object it was called on. Understanding it explains exactly what const member functions actually restrict — and what mutable is the deliberate escape hatch for.

this_const_mutable.cppC++
#include <iostream>
#include <mutex>

class SensorReading {
    double value_;
    mutable int readCount_ = 0;    // mutable = "can change even inside a const method"
    mutable std::mutex cacheMutex_;   // a mutex used purely for internal bookkeeping, not logical state
public:
    SensorReading(double v) : value_(v) {}

    // const member function: 'this' is a POINTER-TO-CONST inside here — it cannot
    // modify value_, and calling this method on a const SensorReading& is allowed
    double getValue() const {
        std::lock_guard<std::mutex> lock(cacheMutex_);  // legal — cacheMutex_ is mutable
        ++readCount_;    // legal ONLY because readCount_ is declared mutable
        return value_;
        // value_ = 0;   would be a COMPILE ERROR here — value_ is NOT mutable
    }

    int getReadCount() const { return readCount_; }

    // Demonstrates 'this' explicitly — rarely needed, but this IS what the compiler
    // inserts implicitly for every member access inside a method
    void setValue(double v) {
        this->value_ = v;   // identical to just writing "value_ = v;"
    }
};

int main() {
    const SensorReading reading(23.5);   // a CONST object
    std::cout << reading.getValue() << "\n";   // OK — getValue() is a const method, callable on a const object
    std::cout << reading.getValue() << "\n";
    std::cout << "Read count (changed despite 'const' object!): " << reading.getReadCount() << "\n";
    return 0;
}
Expected Output
23.5 23.5 Read count (changed despite 'const' object!): 2
💡
Key Takeaway — What mutable Is Actually For const is supposed to mean "the object's logical, observable state doesn't change." mutable is the deliberate, narrow exception for internal bookkeeping that doesn't affect that logical state from the caller's point of view — caching, lazy computation, internal synchronization mutexes, or debug counters. Overusing mutable to sneak around const-correctness for things that do represent real logical state defeats the entire purpose of marking a method const in the first place.

8. Static Members — Variables, Methods & Initialization Order

A static member belongs to the class itself, not to any one instance — there's exactly one copy shared by every object, and it can be accessed even with zero instances alive.

static_members.cppC++
#include <iostream>

class LiftCar {
    static int activeCarCount_;    // declaration only — ONE shared copy for the whole class
    int id_;
public:
    LiftCar() : id_(++activeCarCount_) {}
    ~LiftCar() { --activeCarCount_; }

    int id() const { return id_; }

    // static method — no 'this' pointer, callable without any instance,
    // can ONLY access other static members (there's no object to look up id_ on)
    static int activeCount() { return activeCarCount_; }
};
// Definition (and initialization) — required exactly once, outside the class,
// in a .cpp file. Without this line, you'd get a linker error: undefined reference.
int LiftCar::activeCarCount_ = 0;

int main() {
    std::cout << "Before any car: " << LiftCar::activeCount() << "\n";  // callable with ZERO instances

    LiftCar car1;
    {
        LiftCar car2, car3;
        std::cout << "Active: " << LiftCar::activeCount() << "\n";   // 3
    }
    std::cout << "Active after scope: " << LiftCar::activeCount() << "\n";   // 1
    return 0;
}
Expected Output
Before any car: 0 Active: 3 Active after scope: 1

The Static Initialization Order Fiasco

C++ guarantees static variables within one file are initialized top-to-bottom, but gives no guarantee about the order between static variables defined in different .cpp files. If one global/static object's constructor depends on another global/static object in a different file already being initialized, you have undefined behavior — this is one of the most notorious C++ gotchas, known as the Static Initialization Order Fiasco.

The Fiasco — IllustratedASCII
// file1.cpp
Logger globalLogger;             // constructed at SOME point during static init

// file2.cpp
Config globalConfig(globalLogger); // if file2's statics run FIRST, globalLogger
                                    // isn't constructed yet -> using a not-yet-alive object!

// The C++ standard does NOT define which file's static objects are constructed first.
// This is exactly why the function-local "Meyer's Singleton" pattern (see the
// Design Patterns module) exists: a function-local static is guaranteed to construct
// on its FIRST USE, not at some unspecified point during program startup.
🏛️
Architect's Rule Never let one global/static object's constructor depend on another global/static object defined in a different translation unit. If you need guaranteed, safe initialization order, wrap the dependency in a function-local static accessor (exactly the Meyer's Singleton pattern) instead of a raw global variable.

iterator_categories.cppC++
#include <iostream>
#include <vector>
#include <list>
#include <iterator>

int main() {
    std::vector<int> v = {10, 20, 30, 40};
    auto vit = v.begin();
    vit += 2;                          // random-access: jump directly, O(1) — legal on vector
    std::cout << "vector jumped +2: " << *vit << "\n";  // 30
    std::cout << "random access []: " << vit[-1] << "\n";   // 20 — offset indexing works too

    std::list<int> l = {10, 20, 30, 40};
    auto lit = l.begin();
    // lit += 2;   // COMPILE ERROR — list iterators are only BIDIRECTIONAL, no jump-by-n
    std::advance(lit, 2);              // the CORRECT way — works for ANY iterator category, walks node-by-node for list
    std::cout << "list advanced +2: " << *lit << "\n";   // 30
    --lit;                              // bidirectional: CAN go backward, unlike forward_list
    std::cout << "list after --: " << *lit << "\n";         // 20
    return 0;
}
Expected Output
vector jumped +2: 30 random access []: 20 list advanced +2: 30 list after --: 20
🔴
Iterator Invalidation Rules — Quick Reference vector: any insertion that triggers reallocation invalidates all iterators/pointers/references; without reallocation, insertion invalidates everything from the insertion point onward, and erasure invalidates everything from the erased point onward. deque: insertion/erasure at the ends is safe for most iterators but can invalidate all of them if done in the middle. list/map/set: only iterators to the specifically erased element are invalidated — everything else stays valid, which is a major reason to choose list when you must hold long-lived iterators across modifications.

10. The Standard Exception Hierarchy & noexcept Guarantees

The Exception Handling module already covered try/catch/throw and custom exceptions in depth. Here's the full picture of the built-in hierarchy those custom exceptions plug into, and what a noexcept promise really guarantees.

Standard Exception HierarchyASCII
std::exception
 ├── std::logic_error            (errors detectable BEFORE the program runs, in principle)
 │    ├── std::invalid_argument  (bad argument value)
 │    ├── std::domain_error      (math domain violation, e.g. sqrt of negative)
 │    ├── std::length_error      (attempted size exceeds container's max)
 │    └── std::out_of_range      (index/key outside valid range — e.g. vector::at)
 │
 └── std::runtime_error          (errors only detectable WHILE the program runs)
      ├── std::range_error       (result outside representable range)
      ├── std::overflow_error    (arithmetic overflow)
      └── std::underflow_error   (arithmetic underflow)

std::bad_alloc      — thrown by 'new' on allocation failure (separate branch, not under logic/runtime_error)
std::bad_cast       — thrown by a failed dynamic_cast on a reference (not a pointer)
💡
Practical Guidance You've already used invalid_argument, domain_error, out_of_range, overflow_error, and underflow_error throughout this course — this hierarchy is why catching const std::exception& as a final fallback (seen in the Exception Handling module) correctly catches every one of them: they all inherit from std::exception and share the same what() interface.

What noexcept Actually Guarantees

noexcept_guarantee.cppC++
#include <iostream>
#include <stdexcept>

void promisesNoThrow() noexcept {
    throw std::runtime_error("oops — broke the noexcept promise");
}

int main() {
    std::cout << "About to call a noexcept function that lies...\n";
    promisesNoThrow();   // NOT caught by any try/catch — the program terminates immediately
    std::cout << "This line never runs\n";
    return 0;
}
Actual Program Behavior
About to call a noexcept function that lies... terminate called after throwing an instance of 'std::runtime_error' what(): oops — broke the noexcept promise Aborted (core dumped)
🔴
noexcept Is a Promise, Not a Try/Catch Marking a function noexcept doesn't stop exceptions from being thrown inside it — it tells the compiler you guarantee it won't happen. If that promise is broken, the runtime calls std::terminate() immediately — no stack unwinding, no destructors run cleanly, no catch block anywhere gets a chance, the program just aborts. This is exactly why the Rule of Five module required move constructors and move assignment to be noexcept for vector to trust and use them: the standard library is relying on that promise being genuinely true, not just decorative.

Pointers & Memory Management

What is a Pointer?

A pointer is a variable whose value is a memory address — it points to another object. Unlike references (aliases), pointers are first-class citizens in the type system: they can be null, incremented, reassigned, and cast. Every pointer has a type because the type tells the compiler how many bytes to read/write at that address and how pointer arithmetic scales.

Memory in a C++ process is divided into regions: stack (automatic lifetime, LIFO, fast), heap (dynamic lifetime, managed by you or the allocator, slower), BSS/data (globals/statics), and text (code). Pointers let you reach across all of them.

Declaration, Dereferencing & Address-of

pointers_basics.cpp C++ 
#include <iostream>

int main() {
    int value = 42;

    int* ptr = &value;   // & = address-of operator
    // ptr holds the memory address of 'value'

    std::cout << "value    = " << value    << "\n";  // 42
    std::cout << "&value   = " << &value   << "\n";  // address
    std::cout << "ptr      = " << ptr      << "\n";  // same address
    std::cout << "*ptr     = " << *ptr     << "\n";  // 42 (dereference)

    *ptr = 100;  // Write through the pointer
    std::cout << "value after *ptr=100: " << value << "\n"; // 100

    int* null_ptr = nullptr;  // Prefer nullptr over NULL or 0
    std::cout << "null_ptr is " << (null_ptr ? "not null" : "null") << "\n";

    return 0;
}
Expected Output
value = 42 &value = 0x7fffd4a2bc4c ptr = 0x7fffd4a2bc4c *ptr = 42 value after *ptr=100: 100 null_ptr is null

Pointer Arithmetic

Adding an integer n to a pointer advances it by n × sizeof(T) bytes. This is the foundation of arrays in C++.

pointer_arith.cpp C++ 
#include <iostream>

int main() {
    int arr[] = {10, 20, 30, 40, 50};
    int* p = arr;  // arr decays to &arr[0]

    for (int i = 0; i < 5; ++i) {
        std::cout << "arr[" << i << "] at " << (p+i)
                  << " = " << *(p+i) << "\n";
    }

    // Pointer difference = element count between
    int* start = arr;
    int* end   = arr + 5;
    std::cout << "Distance: " << (end - start) << " elements\n";

    return 0;
}

Memory Fragmentation

Even when the heap holds enough total free bytes, a large allocation can fail — or runtime performance can degrade silently — because the free memory is scattered into many small, non-contiguous gaps. This is memory fragmentation, and it is one of the most critical concepts for embedded and long-running systems programmers.

External vs Internal Fragmentation

TypeWhat causes itWhere space is wasted
External fragmentationMany allocate/free cycles leave isolated free gaps between live blocksBetween allocated blocks — total free space may be enough but no single contiguous chunk fits the request
Internal fragmentationAllocator rounds every request up to a minimum block size (e.g. 8 or 16 bytes)Inside an allocated block — you asked for 5 bytes, got 16; 11 are wasted but "yours"
fragmentation.cppC++
#include <iostream>
#include <vector>

int main() {
    constexpr int N = 8;
    std::vector<int*> blocks;

    // Step 1 — allocate 8 independent small arrays
    for (int i = 0; i < N; ++i)
        blocks.push_back(new int[16]);
    std::cout << "All 8 blocks allocated.\n";

    // Step 2 — free only the EVEN-indexed blocks, leaving gaps between live blocks
    for (int i = 0; i < N; i += 2) {
        delete[] blocks[i];
        blocks[i] = nullptr;
    }
    std::cout << "Freed even-indexed blocks — free space is now fragmented.\n";

    // The heap has 4×16 ints of free space, but each gap is isolated.
    // A single new int[64] may FAIL even though total free bytes would cover it.
    std::cout << "A large contiguous allocation may now fail despite enough total free bytes.\n";

    // Internal fragmentation: ask for 1 byte; allocator silently gives 8–16
    char* tiny = new char(1);
    std::cout << "char(1) at: " << static_cast<void*>(tiny)
              << " (block header + alignment padding add hidden overhead)\n";
    delete tiny;

    for (int i = 1; i < N; i += 2) delete[] blocks[i];
    return 0;
}

How Reference Counting Actually Works — The Control Block

use_count() isn't magic — every shared_ptr that manages the same object shares a pointer to one small heap-allocated struct called the control block. Understanding exactly what's in it, and exactly when each counter changes, is what separates "I know shared_ptr exists" from "I know why my object got destroyed at that specific line."

Control Block LayoutASCII
std::shared_ptr<Node> a = std::make_shared<Node>(42);

  a  ──────┬──────────────►  Control Block  (ONE per managed object, on the heap)
           │                 ┌─────────────────────────────┐
           │                 │ strong_count (atomic) = 1    │  ← how many shared_ptr own the object
           │                 │ weak_count   (atomic) = 0    │  ← how many weak_ptr observe it
           │                 │ deleter                       │  ← how to destroy the object
           │                 │ allocator                     │
           │                 └─────────────────────────────┘
           │
           └──────────────►  Node(42)   ← the actual managed object

std::shared_ptr<Node> b = a;   // COPY constructor: strong_count 1 -> 2 (atomic increment)
                               // 'b' points to the SAME control block AND the same Node

// b goes out of scope        // strong_count 2 -> 1 (atomic decrement) — Node NOT destroyed, count > 0
// a goes out of scope        // strong_count 1 -> 0 -> Node's destructor runs NOW
                               // weak_count is still checked: if it's also 0, the control
                               // block itself is freed too. If any weak_ptr still exist,
                               // the control block survives (just the Node is gone) so that
                               // weak_ptr::expired() can still correctly report "yes, expired."

Exactly When Is the Object Freed? — Proven With a Live Demo

refcount_lifecycle.cppC++
#include <iostream>
#include <memory>

struct Tracked {
    int id;
    Tracked(int i) : id(i) { std::cout << "Tracked(" << id << ") constructed\n"; }
    ~Tracked() { std::cout << "Tracked(" << id << ") DESTROYED — this is the exact moment strong_count hit 0\n"; }
};

int main() {
    std::weak_ptr<Tracked> observer;   // does NOT affect strong_count at all

    {
        std::shared_ptr<Tracked> a = std::make_shared<Tracked>(1);
        observer = a;   // weak_count: 0 -> 1. strong_count still 1 — weak_ptr never counts as ownership
        std::cout << "strong=" << a.use_count() << "\n";   // 1

        {
            std::shared_ptr<Tracked> b = a;   // COPY -> strong_count: 1 -> 2
            std::cout << "strong=" << a.use_count() << "\n";   // 2
        }   // b destroyed -> strong_count: 2 -> 1. Object survives — count is not 0 yet.

        std::cout << "strong after inner scope=" << a.use_count() << "\n";   // 1
        std::cout << "observer expired? " << std::boolalpha << observer.expired() << "\n"; // false

    }   // a destroyed -> strong_count: 1 -> 0 -> ~Tracked() runs HERE, immediately, deterministically

    std::cout << "observer expired now? " << std::boolalpha << observer.expired() << "\n"; // true
    std::cout << "Program continues — control block itself is now freed too, since weak_count also reached 0\n";
    return 0;
}

The Two-Counter Rule — Object Death vs Control Block Death

EventWhat Happens
shared_ptr copiedstrong_count atomically incremented by 1
shared_ptr destroyed/resetstrong_count atomically decremented by 1
weak_ptr created from a shared_ptrweak_count incremented by 1 — does not touch strong_count
weak_ptr destroyedweak_count decremented by 1
strong_count reaches 0The managed object's destructor runs immediately — deterministic, not garbage collected "eventually"
strong_count AND weak_count both reach 0The control block itself is freed — this can happen later than the object's destruction if a weak_ptr outlives all shared_ptrs
🏛️
Why the Increment/Decrement Must Be Atomic If two threads copy the same shared_ptr at the same time, both are incrementing the same strong_count in the control block. Without an atomic increment, this is a classic read-modify-write race — two threads could both read count=1, both write back count=2, and you'd silently lose an increment, eventually causing the object to be destroyed while a live shared_ptr still points to it (a dangling-pointer use-after-free). This is precisely why every shared_ptr copy has real atomic-operation cost — it isn't free, which is the main reason to prefer unique_ptr whenever sole ownership is enough.
💡
Key Takeaway "Reference counting" is really two independent counters in one shared struct, not one. The object dies the instant the strong count hits zero — this is fully deterministic, unlike garbage collection, which is why C++ RAII code can safely put side-effecting cleanup (closing files, releasing locks) directly in a destructor. The control block's own memory is a separate, later event gated by both counters reaching zero.

weak_ptr — Breaking Cyclic References

If two objects hold shared_ptrs to each other, the reference count never reaches zero — a memory leak. weak_ptr is a non-owning observer: it doesn't increment the ref count. To use the object, you must lock() it to get a temporary shared_ptr.

weak_ptr.cpp C++ 
#include <iostream>
#include <memory>

struct B;  // forward declaration

struct A {
    std::shared_ptr<B> b_ptr;
    ~A() { std::cout << "A destroyed\n"; }
};

struct B {
    std::weak_ptr<A> a_ptr;  // weak! breaks the cycle
    ~B() { std::cout << "B destroyed\n"; }
};

int main() {
    auto a = std::make_shared<A>();
    auto b = std::make_shared<B>();

    a->b_ptr = b;   // A holds strong ref to B
    b->a_ptr = a;   // B holds WEAK ref to A (no cycle!)

    // Use weak_ptr safely
    if (auto locked = b->a_ptr.lock()) {  // lock() → shared_ptr
        std::cout << "A is still alive, accessible via lock()\n";
    }

    std::cout << "End of main — destructors fire:\n";
    return 0;
}   // Both A and B properly destroyed
Expected Output
A is still alive, accessible via lock() End of main — destructors fire: A destroyed B destroyed
⚠️
Common Mistake — Raw Pointer to shared_ptr Twice Never create two separate shared_ptrs from the same raw pointer — each will think it's the sole owner and double-delete:
int* raw = new int(5);
shared_ptr<int> s1(raw);
shared_ptr<int> s2(raw); // DISASTER — double free
Always use make_shared or copy an existing shared_ptr.
🏛️
Architect's Rule — Default to unique_ptr In production, 90% of dynamic allocations should use unique_ptr. Only upgrade to shared_ptr when you have a provable need for shared ownership (e.g., a cache, a shared scene graph). Shared ownership is conceptually expensive to reason about and adds atomic operations. Every shared_ptr copy is a memory fence — in hot paths, this matters.

Classes, Constructors & Encapsulation

A class bundles data (members) and behaviour (methods) into a single unit. Encapsulation enforces that internal data is accessed only through controlled interfaces, preventing invalid state. Access specifiers: private (default), protected, public.

#include <stdexcept>
#include <string>

class BankAccount {

    // Constructor with member-initializer list

    std::string owner()     const { return owner_;  }

Inheritance

Inheritance models an is-a relationship. A derived class inherits all non-private members from its base. Use public inheritance to preserve the public interface. protected inheritance is rarely useful and confuses callers.

inheritance.cpp C++ 
#include <iostream>
#include <string>

class Shape {
protected:
    std::string color_;
public:
    Shape(const std::string& c) : color_(c) {}
    // virtual destructor is MANDATORY in base classes
    virtual ~Shape() = default;

    virtual double area() const = 0;  // pure virtual
    virtual std::string describe() const {
        return "Shape[" + color_ + "]";
    }
};

class Circle : public Shape {
    double radius_;
public:
    Circle(const std::string& c, double r)
        : Shape(c), radius_(r) {}

    double area() const override {
        return 3.14159 * radius_ * radius_;
    }
    std::string describe() const override {
        return "Circle[r=" + std::to_string(radius_) + ", " + color_ + "]";
    }
};

class Rectangle : public Shape {
    double w_, h_;
public:
    Rectangle(const std::string& c, double w, double h)
        : Shape(c), w_(w), h_(h) {}

    double area() const override { return w_ * h_; }
    std::string describe() const override {
        return "Rect[" + std::to_string(w_) + "x" + std::to_string(h_) + "]";
    }
};

// Polymorphic function — works for ANY Shape subtype
void printInfo(const Shape& s) {
    std::cout << s.describe() << "  area=" << s.area() << "\n";
}

    printInfo(r);

Rule of Five (Copy/Move Semantics)

If you define any of: destructor, copy constructor, copy assignment, move constructor, move assignment — you should define all five. Modern C++ defaults to the Rule of Zero: let value-type members (string, vector, unique_ptr) handle it automatically, requiring no manual definitions.

rule_of_five.cpp C++ 
#include <iostream>
#include <cstring>

// Classic example: manual buffer ownership
class Buffer {
    char* data_;
    size_t size_;
public:
    // Constructor
    Buffer(const char* str)
        : size_(strlen(str)), data_(new char[size_+1]) {
        memcpy(data_, str, size_+1);
        std::cout << "Constructed: " << data_ << "\n";
    }

    // Destructor
    ~Buffer() {
        std::cout << "Destroyed: " << data_ << "\n";
        delete[] data_;
    }

    // Copy constructor — deep copy
    Buffer(const Buffer& o)
        : size_(o.size_), data_(new char[o.size_+1]) {
        memcpy(data_, o.data_, size_+1);
        std::cout << "Copy ctor: " << data_ << "\n";
    }

    // Move constructor — steal the buffer
    Buffer(Buffer&& o) noexcept
        : size_(o.size_), data_(o.data_) {
        o.data_ = nullptr; o.size_ = 0;
        std::cout << "Move ctor\n";
    }

    // Copy assignment
    Buffer& operator=(const Buffer& o) {
        if (this == &o) return *this;
        delete[] data_;
        size_ = o.size_;
        data_ = new char[size_+1];
        memcpy(data_, o.data_, size_+1);
        return *this;
    }

    // Move assignment
    Buffer& operator=(Buffer&& o) noexcept {
        if (this == &o) return *this;
        delete[] data_;
        data_ = o.data_; size_ = o.size_;
        o.data_ = nullptr; o.size_ = 0;
        return *this;
    }

    const char* get() const { return data_ ? data_ : ""; }
};

int main() {
    Buffer b1("hello");
    Buffer b2 = b1;              // copy ctor
    Buffer b3 = std::move(b1);   // move ctor
    std::cout << "b1: '" << b1.get() << "'  b3: '" << b3.get() << "'\n";
    return 0;
}
Expected Output
Constructed: hello Copy ctor: hello Move ctor b1: '' b3: 'hello' Destroyed: hello Destroyed: hello Destroyed:

Architect's Insight — Prefer Rule of Zero In modern C++, classes should use smart pointers and STL containers as members — they implement all five special operations correctly. Then your class needs zero manual definitions. Only fall back to Rule of Five when wrapping a C resource (file descriptor, socket, GPU handle). That wrapping class becomes a single responsibility utility that the rest of your codebase uses safely.

Constructors — The Full Picture

A constructor's job is to establish the class invariant — the set of conditions that must hold true for every valid object. C++ gives you six flavors, and knowing when each fires (and when the compiler silently generates one for you) is a frequent interview trap.

constructor_types.cpp C++ 
#include <iostream>
#include <string>

class Point {
    double x_, y_;
public:
    // 1. Default constructor
    Point() : x_(0), y_(0) { std::cout << "default\n"; }

    // 2. Parameterized constructor
    Point(double x, double y) : x_(x), y_(y) { std::cout << "param\n"; }

    // 3. Delegating constructor — reuses another ctor of the SAME class
    explicit Point(double uniform) : Point(uniform, uniform) {
        std::cout << "delegating\n";
    }

    // 4. Copy constructor — deep/shallow copy from an lvalue
    Point(const Point& o) : x_(o.x_), y_(o.y_) { std::cout << "copy\n"; }

    // 5. Move constructor — steals resources from an rvalue (temporary)
    Point(Point&& o) noexcept : x_(o.x_), y_(o.y_) { std::cout << "move\n"; }

    double x() const { return x_; }
    double y() const { return y_; }
};

int main() {
    Point a;                 // default
    Point b(3, 4);           // parameterized
    Point c(5.0);            // delegating -> param(5,5)
    Point d = b;             // copy (lvalue source)
    Point e = Point(1, 2);   // move (rvalue source, may be elided)
    return 0;
}
Expected Output
default param param delegating copy
⚠️
Why explicit Matters Without explicit, a single-argument constructor becomes an implicit conversion. void scale(Point p); called as scale(5.0) would silently construct a Point from a raw double — often not what the caller intended. Mark every single-argument (and most multi-argument-with-defaults) constructors explicit unless you deliberately want implicit conversions.
💡
Member Initializer Lists Are Not Optional Style Members are initialized in declaration order (not initializer-list order) before the constructor body runs. Assigning inside the body means the member is first default-constructed, then reassigned — wasted work, and for const or reference members it doesn't even compile. Always prefer the initializer list.

Destructors & Lifecycle Management

A destructor releases whatever resources the constructor acquired — memory, file handles, sockets, locks. It runs automatically when an object leaves scope, is deleted, or its containing object is destroyed. This automatic, deterministic cleanup is the foundation of RAII.

virtual_destructor.cpp C++ 
class Base {
public:
    virtual ~Base() { std::cout << "~Base\n"; }   // virtual!
};
class Derived : public Base {
    int* buffer_ = new int[100];
public:
    ~Derived() override { delete[] buffer_; std::cout << "~Derived\n"; }
};

int main() {
    Base* p = new Derived();
    delete p;   // virtual dtor -> ~Derived then ~Base. Non-virtual -> ~Base ONLY, leak!
}
Expected Output
~Derived ~Base

Destruction order rules to memorize:

  • Members are destroyed in reverse declaration order (opposite of construction).
  • Base classes are destroyed after derived members, in reverse order of derivation.
  • An exception thrown from a destructor while another exception is already propagating calls std::terminate — destructors should never throw.

Encapsulation — Beyond "Make Fields Private"

Encapsulation is not just hiding data; it's guaranteeing an invariant stays true across every public operation. A class that exposes a getter and setter for every private field hasn't encapsulated anything — it's just a struct with extra typing.

invariant.cpp C++ 
// WEAK — no real invariant, just accessors
class TemperatureBad {
    double celsius_;
public:
    void setCelsius(double c) { celsius_ = c; }     // accepts -500°C!
    double getCelsius() const { return celsius_; }
};

// STRONG — invariant enforced at every entry point
class Temperature {
    double celsius_;
    static constexpr double ABSOLUTE_ZERO = -273.15;
public:
    explicit Temperature(double c) : celsius_(c) {
        if (c < ABSOLUTE_ZERO) throw std::invalid_argument("below absolute zero");
    }
    void set(double c) {
        if (c < ABSOLUTE_ZERO) throw std::invalid_argument("below absolute zero");
        celsius_ = c;
    }
    double celsius() const { return celsius_; }
};
🔴
Getter/Setter Pitfall — Returning Internal References std::vector<int>& getItems() { return items_; } hands out a live handle to your internals — any caller can mutate the vector, bypassing every invariant you tried to enforce. Return by value, return a const&, or expose a narrow, intention-revealing API (addItem(), removeItem(id)) instead.

Abstraction — Interfaces Over Implementation

Abstraction means callers depend on what an object does, never how. In C++ this is expressed with an abstract base class: all pure-virtual functions, no data, a virtual destructor.

// Pure interface — zero implementation details leak to callers
class PaymentGateway {
public:

class StripeGateway : public PaymentGateway {

Inheritance — All Six Forms

Inheritance expresses is-a. C++ is one of the few mainstream languages that allows true multiple inheritance, which makes understanding every topology — and its memory layout — essential.

1. Single Inheritance

single.cppASCII + C++
   Animal
     │
     ▼
    Dog

class Animal { public: virtual void speak() const { std::cout<<"..."; } virtual ~Animal()=default; };
class Dog : public Animal { public: void speak() const override { std::cout<<"Woof"; } };

Memory: a Dog object is laid out as [Animal subobject][Dog's own members] — one vptr, one base. Use case: the default, most common form — specializing one concept (a base widget → a button). Advantage: simple, unambiguous, cheap. Mistake: using it for pure code reuse when there's no real is-a relationship (prefer composition then).

2. Multilevel Inheritance

  Animal
    │
    ▼
   Dog
    │
    ▼

         /   |   \

One base, many independent derived classes — exactly the Shape/Circle/Rectangle example already shown above. Use case: plugin/strategy families sharing one interface. Advantage: polymorphic collections (vector<Animal*>). Mistake: forcing unrelated types into one hierarchy just to reuse a helper function — a sign composition is the better fit.

4. Multiple Inheritance

multiple.cppASCII + C++

      \         /
       ▼       ▼
         Duck

A Duck* cast to Swimmable* adjusts the pointer address. Use case: combining independent capabilities (mixins/interfaces). Disadvantage: name clashes between bases require explicit qualification (Duck::Flyable::foo()), and it's the direct cause of the diamond problem below.

It inherits every advantage and every risk of its component forms, especially diamond ambiguity, so it's the form that most benefits from virtual inheritance and careful design review.

The Diamond Problem & Virtual Inheritance

The diamond appears when two classes independently derive from the same base, and a fourth class derives from both.

diamond.cppASCII + C++
            Animal
           /      \
          ▼        ▼
        Dog        Cat        <-- WITHOUT virtual inheritance:
          \        /              Bat contains TWO Animal subobjects
           ▼      ▼               -> bat.name is AMBIGUOUS, memory duplicated
           BatDog

class Animal  { public: std::string name; };
class Dog    : public Animal {};   // non-virtual
class Cat    : public Animal {};   // non-virtual
class BatDog : public Dog, public Cat {};

BatDog b;
// b.name;              // ERROR: ambiguous — which Animal::name?
b.Dog::name = "Rex";    // must disambiguate explicitly
b.Cat::name = "Whiskers";
diamond_fixed.cppC++
// FIX: virtual inheritance — Dog and Cat share ONE Animal subobject
class Animal { public: std::string name; };
class Dog : virtual public Animal {};
class Cat : virtual public Animal {};
class BatDog : public Dog, public Cat {};

BatDog b;
b.name = "Rex";   // OK — exactly one Animal, no ambiguity
🏛️
How Virtual Inheritance Actually Works Each virtually-derived class stores a hidden pointer (a "vbase offset") to the shared base subobject instead of embedding it directly. The most-derived class (BatDog) becomes responsible for constructing the shared Animal exactly once — even though both Dog and Cat list it in their initializer lists, C++ ignores those and lets BatDog's constructor initialize it. This adds one indirection per access and slightly larger objects — pay this cost only when the diamond genuinely represents shared identity, not by default.
🔴
Interview Trap — Construction Order With Virtual Bases Virtual base subobjects are always constructed before any non-virtual base, by the most-derived class, regardless of where they appear in the inheritance list. Forgetting this is a classic source of "why did my base constructor run twice / not at all" bugs.

Polymorphism — Compile-Time vs Runtime

Compile-time (static) polymorphism is resolved by the compiler and has zero runtime cost: function overloading, operator overloading, and templates. Runtime (dynamic) polymorphism is resolved via the vtable, at the cost of one indirection per call.

overloading.cppC++
// Function overloading — same name, different parameter types (compile-time)
void print(int i)          { std::cout << "int: "    << i << "\n"; }
void print(double d)       { std::cout << "double: " << d << "\n"; }
void print(const std::string& s) { std::cout << "string: " << s << "\n"; }

// Operator overloading — gives user types natural syntax
struct Vec2 {
    double x, y;
    Vec2 operator+(const Vec2& o) const { return {x+o.x, y+o.y}; }
    bool operator==(const Vec2& o) const { return x==o.x && y==o.y; }
    friend std::ostream& operator<<(std::ostream& os, const Vec2& v) {
        return os << "(" << v.x << ", " << v.y << ")";
    }
};

int main() {
    print(42); print(3.14); print(std::string("hi"));
    Vec2 a{1,2}, b{3,4};
    std::cout << (a + b) << "\n";   // (4, 6)
}
💡
Operator Overloading Best Practices Keep operators behaving as users expect: operator+ should not mutate its operands, operator== should be consistent with operator!=, and comparison/arithmetic operators are usually free functions (or friend) while compound-assignment (+=) and subscript (operator[]) are members. Never overload &&, ||, or , — you lose short-circuit/sequencing guarantees.

Object Slicing

slicing.cppC++
void bad(Shape s) {        // pass BY VALUE — slices!
    std::cout << s.area();     // always calls Shape::area — Circle/Rectangle parts are GONE
}
Circle c("red", 5.0);

Slicing happens whenever a derived object is copied into a base-typed value (parameter, return, container element). The fix is always the same: pass/store by reference or pointer (raw, or better, smart pointer) when polymorphism is needed — std::vector<std::unique_ptr<Shape>>, never std::vector<Shape>.

RTTI & dynamic_cast

rtti.cppC++
void handle(Shape* s) {
    if (auto* c = dynamic_cast<Circle*>(s)) {   // nullptr if s is NOT a Circle

⚠️
RTTI Is a Design Smell (Usually) dynamic_cast requires RTTI (runtime overhead, larger binaries) and, more importantly, means your code is asking "what concrete type are you?" instead of "what can you do?" — a violation of polymorphism itself. Reach for a virtual function first; reserve dynamic_cast for genuine cross-cutting cases like visitor patterns or plugin systems where the type set is closed and known.

Composition Over Inheritance

composition.cppC++
// Inheritance (is-a) — tightly couples Car to Engine's interface and lifetime
class CarBad : public Engine { /* a Car IS NOT an Engine — wrong relationship */ };

// Composition (has-a) — Car owns an Engine, can swap implementations freely
class Car {
    std::unique_ptr<Engine> engine_;   // any Engine subtype — Petrol, Electric...
public:
    explicit Car(std::unique_ptr<Engine> e) : engine_(std::move(e)) {}
    void start() { engine_->ignite(); }
};

Rule of thumb: use inheritance only for genuine is-a relationships where substitutability (the Liskov Substitution Principle) holds. Use composition for has-a / "is-implemented-in-terms-of" relationships — it's more flexible, avoids fragile base classes, and keeps hierarchies shallow. This directly motivates the Dependency Inversion Principle: Car depends on the Engine abstraction, not a concrete engine, so new engine types plug in with zero changes to Car.

9. Friendship — friend Functions & friend Classes

friend grants a specific external function or class access to your class's private/protected members — a deliberate, explicit exception to encapsulation, not a general loophole.

friendship.cppC++
#include <iostream>

class Engine {
    double temperature_ = 70.0;   // private — normally inaccessible from outside

    // friend FUNCTION — this one specific free function may access Engine's private members
    friend void calibrate(Engine& e);

    // friend CLASS — grants EVERY method of DiagnosticsTool access to Engine's privates
    friend class DiagnosticsTool;
};

void calibrate(Engine& e) {
    e.temperature_ = 72.5;    // legal ONLY because of the friend declaration above
    std::cout << "Calibrated to " << e.temperature_ << "\n";
}

class DiagnosticsTool {
public:
    void inspect(const Engine& e) {
        std::cout << "Diagnostics reading private temperature_: " << e.temperature_ << "\n";
    }
};

int main() {
    Engine engine;
    calibrate(engine);

    DiagnosticsTool tool;
    tool.inspect(engine);
    return 0;
}
Expected Output
Calibrated to 72.5 Diagnostics reading private temperature_: 72.5
When to UseWhen to Avoid
Operator overloads that need symmetric access (e.g. operator<< for printing, seen in the OOP module's Vector2D example)As a general workaround for "I don't want to write getters" — it breaks encapsulation for every future maintainer
A tightly-coupled helper/test class that legitimately needs deep access (a dedicated DiagnosticsTool or unit test fixture)Between classes that aren't genuinely part of the same tight-knit subsystem
Builder/factory classes that construct an object in stages before it's "complete"Whenever a public method could achieve the same thing just as easily
⚠️
Common Pitfall Friendship is not inherited and not transitive: if B is a friend of A, and C derives from B, C does not automatically gain access to A's privates. Each friend relationship must be declared explicitly by the class granting access.

Why Initializer Lists Matter — Not Just Style, Real Performance

initializer_list_performance.cppC++
#include <iostream>
#include <string>

struct Loud {
    std::string data;
    Loud() { std::cout << "  Loud default-constructed\n"; }
    Loud(const std::string& s) : data(s) { std::cout << "  Loud constructed from string\n"; }
    Loud& operator=(const std::string& s) { data = s; std::cout << "  Loud ASSIGNED from string\n"; return *this; }
};

class BadWay {
    Loud member_;
public:
    BadWay(const std::string& s) {
        member_ = s;   // member_ is ALREADY default-constructed by the time we reach here —
                          // this line then does a SECOND operation: an assignment
    }
};

class GoodWay {
    Loud member_;
public:
    GoodWay(const std::string& s) : member_(s) {   // constructs member_ directly from s — ONE operation total
    }
};

int main() {
    std::cout << "BadWay (assignment in body):\n";
    BadWay b("sensor-1");        // default-construct member_, THEN assign — 2 operations

    std::cout << "GoodWay (member initializer list):\n";
    GoodWay g("sensor-2");       // construct member_ directly with the right value — 1 operation
    return 0;
}
Expected Output
BadWay (assignment in body): Loud default-constructed Loud ASSIGNED from string GoodWay (member initializer list): Loud constructed from string
💡
Key Takeaway Every class-type member without an initializer list entry gets default-constructed first, before the constructor body even starts running — assigning to it in the body is then a wasted second operation. For expensive members (strings, vectors, other objects), this doubles the work for no benefit. Initializer lists aren't just neater syntax — they construct each member exactly once, directly with its final value. This is also the only way to initialize const members and reference members, both of which cannot be assigned to after construction.

11. Abstract Classes & Interfaces

A class with at least one pure virtual function (= 0) is abstract: it cannot be instantiated directly, and exists purely to define a contract that derived classes must implement. A class where every method is pure virtual (no data, no implemented behavior) is effectively an interface — the OOP module's Shape class and the Design Patterns module's IObserver are both real examples of this already used earlier in the course.

Function Overriding vs Function Overloading — The Complete Picture

These two terms are frequently confused in interviews. They are completely different mechanisms, resolved at different times, for different purposes.

overload_vs_override.cppC++
#include <iostream>

// ── OVERLOADING — same scope, different signatures ──────────────────────
void log(int code)              { std::cout << "[LOG] code="    << code    << "\n"; }
void log(const std::string& msg) { std::cout << "[LOG] msg="     << msg     << "\n"; }
void log(double val, int prec)  { std::cout << "[LOG] val="     << val     << "\n"; }
// Resolved at compile time — the compiler looks at argument types
// and selects the matching overload. Zero runtime cost.

// ── OVERRIDING — derived class replaces a base virtual function ──────────
struct Sensor {
    virtual void read() const { std::cout << "Sensor::read (default)\n"; }
    virtual ~Sensor() = default;
};

struct TemperatureSensor : Sensor {
    void read() const override { std::cout << "TemperatureSensor::read (25°C)\n"; }
    // 'override' tells the compiler: I intend to override a base virtual function.
    // If the signature doesn't match (e.g. missing const), COMPILE ERROR — not a silent new function.
};

struct PressureSensor : Sensor {
    void read() const override { std::cout << "PressureSensor::read (1013 hPa)\n"; }
};

int main() {
    // Overloading — which log() is called is decided here by the compiler
    log(42);
    log(std::string("Motor started"));
    log(98.6, 1);

    // Overriding — which read() is called is decided at RUNTIME by the vtable
    Sensor* s1 = new TemperatureSensor();
    Sensor* s2 = new PressureSensor();
    s1->read();   // calls TemperatureSensor::read — runtime dispatch
    s2->read();   // calls PressureSensor::read   — runtime dispatch
    delete s1; delete s2;
    return 0;
}
Expected Output
[LOG] code=42 [LOG] msg=Motor started [LOG] val=98.6 TemperatureSensor::read (25°C) PressureSensor::read (1013 hPa)
🔴
The Silent Bug — Hiding Instead of Overriding If you define a function in a derived class with the same name as a base function but a different signature — and forget override — the compiler silently creates a new, unrelated function that hides the base one. Calling through a base pointer still dispatches to the base version. override turns this silent bug into a compile error. Always use it.

Operator Overloading — In Depth

Operator overloading lets user-defined types support the same natural syntax as built-in types. When you write v1 + v2 on a custom vector class, the compiler translates it to v1.operator+(v2) — an ordinary function call you wrote. This is pure compile-time dispatch; it adds zero runtime overhead.

Member vs Free-Function Operators

operator_overload.cppC++
#include <iostream>
#include <string>

class Vector2 {
public:
    double x, y;
    Vector2(double x_, double y_) : x(x_), y(y_) {}

    // ── MEMBER operator: left operand is implicitly *this ──────────────
    // Compound-assignment, subscript, call — always members.
    Vector2& operator+=(const Vector2& o) {
        x += o.x; y += o.y;
        return *this;   // return *this to allow chaining: a += b += c
    }

    // Unary negation — member (no second operand)
    Vector2 operator-() const { return {-x, -y}; }

    // Comparison (C++20: can auto-generate all six from <=> spaceship)
    bool operator==(const Vector2& o) const { return x == o.x && y == o.y; }

    // ── FREE-FUNCTION operator (friend for private access) ─────────────
    // Binary arithmetic: both operands are parameters — symmetric, works when
    // left operand is NOT the class type (e.g. 3.0 + vec).
    friend Vector2 operator+(Vector2 lhs, const Vector2& rhs) {
        lhs += rhs;   // reuse += defined above
        return lhs;
    }

    // Stream insertion — MUST be a free function: left operand is ostream, not Vector2
    friend std::ostream& operator<<(std::ostream& os, const Vector2& v) {
        return os << "(" << v.x << ", " << v.y << ")";
    }
};

int main() {
    Vector2 a{1.0, 2.0}, b{3.0, 4.0};

    std::cout << "a + b = " << (a + b) << "\n";          // (4, 6)
    std::cout << "-a    = " << (-a)    << "\n";          // (-1, -2)
    a += b;
    std::cout << "a after +=: " << a << "\n";           // (4, 6)
    std::cout << std::boolalpha << (a == b) << "\n";     // false
    return 0;
}
Expected Output
a + b = (4, 6) -a = (-1, -2) a after +=: (4, 6) false

The built-in a && b does not evaluate b if a is false; an overloaded operator&& evaluates both arguments before calling the function. , (comma) — overloading removes the guaranteed left-to-right evaluation order. & (unary address-of) — overloading breaks compatibility with standard library code that assumes &obj returns a real pointer.

lvalue, rvalue & Reference Collapsing

Every C++ expression has a value category that determines whether it can appear on the left of =, whether it can bind to an rvalue reference, and whether the compiler will apply move semantics. Misunderstanding this is the root cause of most move-semantics bugs.

Value Categories at a Glance

CategoryDefinitionExamplesCan take address?
lvalueHas a persistent identity (a name, a memory location that outlives the expression)Named variables, *ptr, arr[i], function call returning T&Yes
prvalue (pure rvalue)A temporary with no persistent identity — its value is used immediately then discardedLiterals (42, 3.14), a + b, function call returning T (by value)No
xvalue ("expiring" value)An object whose resources can be stolen — it has identity but is about to expirestd::move(x), function returning T&&Yes (but shouldn't be used after)

lvalue + xvalue = glvalue (generalised lvalue — has identity). prvalue + xvalue = rvalue (can bind to T&&).

lvalue_rvalue_overloading.cppC++
#include <iostream>
#include <string>

// Overload on value category — the compiler picks based on what the caller passes
void process(const std::string& s) {     // lvalue overload: binds to named objects
    std::cout << "lvalue: " << s << "\n";
}
void process(std::string&& s) {           // rvalue overload: binds to temporaries / std::move()
    std::cout << "rvalue (can steal): " << s << "\n";
}

int main() {
    std::string name = "Praveen";

    process(name);                     // lvalue — 'name' has a name, lives beyond this call
    process(std::string("temporary")); // prvalue — temporary has no name
    process(std::move(name));          // xvalue — 'name' cast to rvalue; may be left in valid-but-empty state

    std::cout << "name after move: '" << name << "'\n";  // "" — moved-from state

    // lvalue reference: only binds to lvalues
    int x = 10;
    int& lref = x;          // OK — x is an lvalue
    // int& bad = 42;        // ERROR — 42 is a prvalue; lvalue ref can't bind to it

    // rvalue reference: only binds to rvalues (temporaries / moved-from)
    int&& rref = 42;        // OK — extends the lifetime of the temporary 42
    int&& rref2 = x + 1;   // OK — x+1 is a prvalue
    // int&& bad2 = x;       // ERROR — x is an lvalue, not an rvalue
    std::cout << "rref=" << rref << " rref2=" << rref2 << "\n";
    return 0;
}

Reference Collapsing — The Rule That Makes Perfect Forwarding Work

When template deduction or typedef creates "a reference to a reference," the language applies reference collapsing to produce a single valid reference. The rule is simple: if either reference is an lvalue reference, the result is an lvalue reference.

Collapsed FromResultIntuition
T& &T&lvalue wins
T& &&T&lvalue wins
T&& &T&lvalue wins
T&& &&T&&only rvalue if both are rvalue
reference_collapsing.cppC++
#include <iostream>
#include <utility>

// Universal reference (T&& in a deduced context) captures EITHER lvalue OR rvalue.
// When T is deduced as int&, T&& collapses to int& && = int& (lvalue).
// When T is deduced as int,  T&& stays as int&& (rvalue).
template<typename T>
void wrapper(T&& arg) {              // T&& is a "forwarding reference" here
    process(std::forward<T>(arg));   // perfect-forwards: preserves value category
}

void process(const std::string& s) { std::cout << "lvalue: " << s << "\n"; }
void process(std::string&& s)       { std::cout << "rvalue: " << s << "\n"; }

int main() {
    std::string s = "hello";
    wrapper(s);               // T deduced as string& → T&& = string& → lvalue overload
    wrapper(std::move(s));    // T deduced as string  → T&& = string&& → rvalue overload
    wrapper(std::string("x")); // T deduced as string  → rvalue overload
    return 0;
}
Expected Output
lvalue: hello rvalue: hello rvalue: x
🏛️
std::move vs std::forward — The One-Line Rule std::move(x) is an unconditional cast to rvalue — use it when transferring ownership. std::forward<T>(x) conditionally casts to rvalue only if the original argument was an rvalue — use it inside templates to preserve the caller's value category (perfect forwarding). Using std::move inside a template wrapper would turn lvalue arguments into rvalues, silently moving from objects the caller still needs.

Exception Handling & RAII

RAII (Resource Acquisition Is Initialization) is perhaps the most important C++ idiom. It ties resource lifetimes to object lifetimes: acquire in the constructor, release in the destructor. Since destructors run even when an exception unwinds the stack, RAII makes code automatically exception-safe.

try / catch / throw — Basics

exceptions.cpp C++ 
#include <iostream>
#include <stdexcept>
#include <string>

double safeDivide(double a, double b) {
    if (b == 0.0)
        throw std::domain_error("Division by zero");
    return a / b;
}

void processFile(const std::string& name) {
    if (name.empty())
        throw std::invalid_argument("Filename is empty");
    throw std::runtime_error("File not found: " + name);
}

int main() {
    // Catch specific exceptions
    try {
        std::cout << safeDivide(10, 2) << "\n";  // 5
        std::cout << safeDivide(10, 0) << "\n";  // throws
    } catch (const std::domain_error& e) {
        std::cout << "Domain error: " << e.what() << "\n";
    }

    // Catch hierarchy (most specific first)
    try {
        processFile("config.json");
    } catch (const std::invalid_argument& e) {
        std::cout << "Invalid arg: " << e.what() << "\n";
    } catch (const std::runtime_error& e) {
        std::cout << "Runtime: "    << e.what() << "\n";
    } catch (const std::exception& e) {
        std::cout << "std::exception: " << e.what() << "\n";
    } catch (...) {
        std::cout << "Unknown exception!\n";
    }

    // Re-throw
    try {
        try { throw std::runtime_error("inner"); }
        catch (...) {
            std::cout << "Caught, rethrowing...\n";
            throw;  // re-throw same exception
        }
    } catch (const std::exception& e) {
        std::cout << "Caught after rethrow: " << e.what() << "\n";
    }
    return 0;
}

Templates are C++'s compile-time generics. They let you write code parameterised by types (or values), and the compiler generates concrete instantiations as needed. This gives you zero-runtime-cost abstraction — the performance of hand-written specialised code with the ergonomics of generic programming.

#include <iostream>
#include <stdexcept>

template<typename T, size_t Capacity>
class RingBuffer {
    T     data_[Capacity];
    size_t head_ = 0, tail_ = 0, count_ = 0;
public:
    void push(const T& val) {
        if (count_ == Capacity) throw std::overflow_error("Ring buffer full");
        data_[tail_] = val;
        tail_ = (tail_ + 1) % Capacity;
        ++count_;
    }
    T pop() {
        if (count_ == 0) throw std::underflow_error("Ring buffer empty");
        T val = data_[head_];
        head_ = (head_ + 1) % Capacity;
        --count_;
        return val;
    }
    size_t size() const { return count_; }
    bool   empty() const { return count_ == 0; }
};

int main() {
    RingBuffer<int, 4> rb;
    rb.push(10); rb.push(20); rb.push(30);
    std::cout << "size=" << rb.size() << "\n";
    std::cout << rb.pop() << " " << rb.pop() << "\n";

    // Works for strings too!
    RingBuffer<std::string, 3> srb;
    srb.push("alpha"); srb.push("beta");
    std::cout << srb.pop() << "\n";
    return 0;
}

Variadic Templates & Parameter Packs

A variadic template accepts any number of type parameters via a parameter pack (typename... Args). Combined with fold expressions (C++17), they replace error-prone recursive metaprogramming with clean, single-expression code. This is how std::make_tuple, std::printf-replacement formatting, and std::variant are built.

variadic_templates.cppC++
#include <iostream>

// Fold expression (C++17): operate on all pack elements in one expression
template<typename... Args>
auto sum(Args... args) {
    return (... + args);          // unary left fold: ((args[0]+args[1])+args[2])+...
}

template<typename... Args>
void printAll(Args&&... args) {
    ((std::cout << args << " "), ...);  // comma fold: left-to-right evaluation
    std::cout << "\n";
}

// Recursive variadic template (pre-C++17 style — still important to understand)
template<typename T>
void printRec(const T& first) { std::cout << first << "\n"; }
template<typename T, typename... Rest>
void printRec(const T& first, Rest&&... rest) {
    std::cout << first << " | ";
    printRec(std::forward<Rest>(rest)...);  // peel one element, recurse on the rest
}

// sizeof... — number of elements in a pack (compile-time constant)
template<typename... Ts>
constexpr auto packSize() { return sizeof...(Ts); }

int main() {
    std::cout << sum(1, 2, 3, 4, 5) << "\n";      // 15
    printAll(42, "hello", 3.14, true);
    printRec(10, 20, 30);
    std::cout << "Pack size <int,double,char>: "
              << packSize<int, double, char>() << "\n";
    return 0;
}

if constexpr — Compile-Time Branching

if constexpr (C++17) lets a template have branches that are discarded at compile time. The discarded branch is never instantiated — it may legally contain code that would not compile for the given type, because the compiler never tries.

if_constexpr.cppC++
#include <iostream>
#include <type_traits>
#include <string>

template<typename T>
void describe(const T& val) {
    if constexpr (std::is_integral_v<T>) {
        std::cout << "Integer: " << val << " (even? "
                  << std::boolalpha << (val % 2 == 0) << ")\n";
        // val % 2 would be a compile error for string — but this branch is
        // DISCARDED when T is not integral, so it never sees a string.
    } else if constexpr (std::is_floating_point_v<T>) {
        std::cout << "Float: " << val << " (truncated: "
                  << static_cast<long long>(val) << ")\n";
    } else {
        std::cout << "Other: " << val << "\n";
    }
}

template<int N>
constexpr int factorial() {
    if constexpr (N <= 1) return 1;
    else                   return N * factorial<N - 1>();
}

int main() {
    describe(42);
    describe(3.14);
    describe(std::string("hello"));
    constexpr int f5 = factorial<5>();   // zero runtime cost
    std::cout << "5! = " << f5 << "\n";
    return 0;
}

Template Metaprogramming (TMP) — Basics

TMP uses the template system as a compile-time computation engine. Types, integer constants, and type transformations are resolved at compile time with zero runtime cost. <type_traits> is TMP in action — the entire header is compile-time template logic.

template_metaprogramming.cppC++
#include <iostream>
#include <type_traits>

// Compile-time Fibonacci — computed entirely at compile time via template recursion
template<int N> struct Fib {
    static constexpr int value = Fib<N-1>::value + Fib<N-2>::value;
};
template<> struct Fib<0> { static constexpr int value = 0; };
template<> struct Fib<1> { static constexpr int value = 1; };

// Type traits — compile-time type inspection
template<typename T>

    std::cout << "is_pointer:    " << std::boolalpha << std::is_pointer_v<T>     << "\n"
              << "is_const:      "                   << std::is_const_v<T>      << "\n"
              << "is_arithmetic: "                   << std::is_arithmetic_v<T> << "\n";
    using Mutable = std::remove_const_t<T>;
    std::cout << "remove_const same as int? " << std::is_same_v<Mutable, int> << "\n";
}

// (C++20 Concepts are the modern ergonomic replacement for this pattern)

Standard Template Library (STL)

The STL is C++'s standard library of generic algorithms, containers, and iterators. It's built on the Iterator Pattern: algorithms operate on half-open ranges [begin, end) and don't care about the container type — only that it provides iterators. This separation enables massive code reuse.

std::vector — The Complete Reference

vector is the container you'll reach for 90% of the time, so it's worth understanding completely rather than through one example. Underneath, a vector is just three pointers/values wrapped in a class:

vector memory modelASCII
std::vector<int> v;             conceptually, a vector object holds:

┌─────────────────────────┐
│ data_  ───────────────► │───► [ 10 | 20 | 30 |  ?  |  ?  ]   ← heap-allocated buffer
│ size_     = 3           │      ^                    ^
│ capacity_ = 5           │      3 elements in use     2 unused slots (already allocated)
└─────────────────────────┘

- size()     -> how many elements are ACTUALLY stored (3)
- capacity() -> how many elements the buffer CAN hold before reallocating (5)
- data()     -> raw pointer to the first element — the buffer is guaranteed CONTIGUOUS

When size_ == capacity_ and you push_back() again:
  1. Allocate a NEW, bigger buffer (typically ~1.5x–2x the old capacity)
  2. Move (or copy, if not noexcept-movable) every existing element into it
  3. Destroy the old elements, free the old buffer
  4. ALL pointers, references, and iterators into the old buffer are now DANGLING
  This is why "amortized O(1)" push_back sometimes costs O(n) — but rarely enough that the
  AVERAGE cost per push stays constant.
🏛️
Why "Amortized" O(1)? If capacity always grows by a constant multiplier (e.g. ×2) rather than a fixed amount, the total cost of copying elements across all reallocations up to size n sums to O(n), not O(n²) — spread across n pushes, that's O(1) per push on average, even though any single push that triggers reallocation costs O(n) in that instant. If the growth factor were additive (e.g. +1 slot each time) instead of multiplicative, this guarantee would break and you'd get true O(n) amortized cost.

Constructing a vector

vector_construction.cppC++
std::vector<int> a;                          // empty, size=0, capacity=0 (usually)
std::vector<int> b(5);                       // 5 elements, all value-initialized to 0
std::vector<int> c(5, 42);                   // 5 elements, all set to 42

std::vector<std::vector<int>> grid(3, std::vector<int>(4, 0)); // 3x4 grid of zeros
⚠️
{} vs () — The Classic Gotcha std::vector<int> v(5, 10); creates 5 elements each equal to 10. std::vector<int> v{5, 10}; creates a 2-element vector {5, 10} instead — because a brace-init list with elements matching the value type takes priority over the (size, value) constructor. This single-character difference is a very common bug.

operator[] vs at() — When to Use Which Use operator[] in hot loops where you've already validated the index (e.g. a bounded for loop) — it compiles to a raw pointer offset with zero overhead. Use at() at boundaries where the index comes from untrusted input (user data, file parsing, network) and you want a safe, catchable failure instead of undefined behaviour.

Modifiers — inserting, removing, building up a vector

vector_modifiers.cppC++
std::vector<std::string> v = {"b", "c"};

v.push_back("d");                 // copies/moves an already-constructed string to the end
v.emplace_back(3, 'x');            // constructs std::string(3,'x') DIRECTLY in place — no temporary

v.insert(v.begin(), "a");        // insert BEFORE begin() -> {"a","b","c","d","xxx"} — O(n), shifts everything right
v.insert(v.begin()+2, 2, "Z");   // insert 2 copies of "Z" at index 2

v.pop_back();                     // removes last element — O(1), does NOT return the removed value
v.erase(v.begin());               // removes element at begin() — O(n), shifts everything left
v.erase(v.begin(), v.begin()+2);  // erase a RANGE [first, last)

v.assign(3, "same");              // replaces ALL contents with 3 copies of "same"
v.clear();                        // removes all elements, size()->0, capacity() typically unchanged

// swap — O(1), just exchanges internal pointers, no element copying at all
std::vector<int> x = {1,2}, y = {9,9,9};
x.swap(y);                        // x is now {9,9,9}, y is now {1,2}
🔴
push_back vs emplace_back push_back takes an already-constructed object (or something implicitly convertible) and copies/moves it in. emplace_back forwards its arguments directly to the element type's constructor, building the object in place inside the vector's buffer — skipping an extra temporary and a move. Prefer emplace_back when constructing non-trivial objects directly from constructor arguments.

std::map & std::unordered_map — Full Operations

map keeps keys sorted (red-black tree, O(log n) operations); unordered_map uses a hash table (O(1) average, O(n) worst case on hash collisions) and gives no ordering guarantee at all. Both share almost the same interface.

map_full_ops.cppC++
std::map<std::string, int> m;

// Insertion — three different ways, each with different behaviour on existing keys
m["a"] = 1;                       // operator[]: inserts "a" with value 0 first if absent, THEN assigns 1
m.insert({"b", 2});               // insert: does NOTHING if "b" already exists (no overwrite)
m.emplace("c", 3);                // emplace: constructs the pair in place, also skips if key exists
m.insert_or_assign("a", 99);       // C++17: inserts OR overwrites — the one you usually actually want

// Lookup — three ways, very different semantics
int v1 = m["a"];                   // operator[]: INSERTS "a"=0 if missing — dangerous for read-only lookups!
auto it = m.find("z");            // find: returns m.end() if missing — does NOT insert. Safe for lookups.
if (it != m.end()) std::cout << it->second;
bool has = m.contains("a");       // C++20: clean existence check, no insertion risk
size_t cnt = m.count("a");        // pre-C++20 existence check — 0 or 1 for map (map has unique keys)

// Iteration — map iterates in SORTED key order automatically
for (const auto& [key, value] : m) std::cout << key << "=" << value << " ";

// Removal
m.erase("b");                    // erase by key
m.erase(m.begin());               // erase by iterator

// Ordered-map-only: range queries (unordered_map has none of these — no ordering to query)
std::map<int, std::string> scores = {{10,"a"},{20,"b"},{30,"c"}};
auto lb = scores.lower_bound(15);  // first element with key >= 15  -> {20,"b"}
auto ub = scores.upper_bound(20);  // first element with key >  20  -> {30,"c"}

std::multiset & std::multimap — Full Operations

multiset and multimap are the "allow duplicates" siblings of set and map. Same red-black tree, same O(log n) guarantees, same sorted iteration order — the only difference is that a key can appear more than once. This changes how you must search and erase, which is exactly what interviewers probe.

multiset_full_ops.cppC++
#include <iostream>
#include <set>

int main() {
    std::multiset<int> ms = {5, 1, 3, 1, 5, 1};   // duplicates KEPT -> {1,1,1,3,5,5}

    ms.insert(1);                     // always succeeds — no uniqueness check, unlike set::insert
    std::cout << "count of 1: " << ms.count(1) << "\n";  // 4 — count() can exceed 1, unlike in set/map

    // erase(value) removes ALL matching entries — a common surprise
    size_t removed = ms.erase(1);
    std::cout << "removed " << removed << " copies of 1\n";      // removed 4 copies of 1

    // To remove only ONE occurrence, erase by iterator instead
    ms.insert(5); ms.insert(5);        // {3,5,5,5}
    auto it = ms.find(5);            // find() returns the FIRST matching iterator
    if (it != ms.end()) ms.erase(it);   // erase just that one -> {3,5,5}

    std::cout << "Final multiset: ";
    for (int x : ms) std::cout << x << " ";
    std::cout << "\n";

    // equal_range — get ALL iterators pointing to a given key at once
    auto [lo, hi] = ms.equal_range(5);
    std::cout << "Number of 5s via equal_range: " << std::distance(lo, hi) << "\n";
    return 0;
}

std::pair — The Simplest Compound Type

std::pair<T1, T2> bundles exactly two values of (possibly different) types into one object. It's what map's elements actually are under the hood (pair<const Key, Value>), and what many STL algorithms return when they need to hand back two pieces of information at once.

pair_full_ops.cppC++
#include <iostream>
#include <utility>
#include <string>
#include <vector>
#include <algorithm>

int main() {
    // Construction — three equivalent ways
    std::pair<std::string, int> p1("Praveen", 28);
    auto p2 = std::make_pair("Amit", 31);         // type deduced automatically
    std::pair<std::string, int> p3{"Divya", 26};    // brace-init, C++11 onward

    // Access — .first and .second, always, regardless of what T1/T2 are
    std::cout << p1.first << " is " << p1.second << " years old\n";

    // Structured bindings (C++17) — much more readable than .first/.second
    auto& [name, age] = p1;
    age = 29;   // modifies p1.second directly, since the binding is a reference
    std::cout << p1.first << " is now " << p1.second << "\n";

    // Comparison — pairs compare lexicographically: first by .first, then by .second
    std::cout << std::boolalpha << "p1 < p2: " << (p1 < p2) << "\n";

    // Sorting a vector of pairs by the second element using a lambda comparator
    std::vector<std::pair<std::string, int>> people = {p1, p2, p3};
    std::sort(people.begin(), people.end(),
              [](const auto& a, const auto& b) { return a.second < b.second; });
    for (const auto& [n, a] : people) std::cout << n << ":" << a << " ";
    std::cout << "\n";

    // A function returning two values — the classic use case
    auto minMax = [](const std::vector<int>& v) -> std::pair<int,int> {
        auto [minIt, maxIt] = std::minmax_element(v.begin(), v.end());
        return {*minIt, *maxIt};
    };
    auto [lo, hi] = minMax({4, 1, 9, 3});
    std::cout << "min=" << lo << " max=" << hi << "\n";
    return 0;
}

std::tuple — Pair Generalized to N Elements

std::tuple extends pair from exactly two elements to any fixed number, each with its own independent type. Use it when a function needs to return three or more related values without writing a dedicated struct for a one-off case.

#include <string>

std::tuple<bool, std::string, int> parseHeader(const std::string& line) {
    if (line.empty()) return {false, "", 0};
    return {true, "OK", static_cast<int>(line.size())};
}

    std::tuple<int, std::string, double> t1(1, "Motor", 3.5);

    std::cout << std::get<std::string>(t1) << "\n";  // works because only ONE string field exists

    // Structured bindings — the modern, readable way to unpack a tuple (C++17)
    auto [ok, message, length] = parseHeader("GET /status HTTP/1.1");
    std::cout << std::boolalpha << "ok=" << ok << " msg=" << message << " len=" << length << "\n";

    std::cout << (t1 < t2) << "\n";

std::deque — Double-Ended Queue

A deque is a sequence of fixed-size chunks, giving O(1) insertion/removal at both ends (unlike vector, which is only O(1) amortized at the end).

deque_full_ops.cppC++
std::deque<int> dq = {2, 3, 4};

dq.push_front(1);      // O(1) — {1,2,3,4} — vector CANNOT do this in O(1)
dq.push_back(5);       // O(1) — {1,2,3,4,5}
dq.pop_front();          // O(1) — {2,3,4,5}
dq.pop_back();           // O(1) — {2,3,4}
dq[1];                 // O(1) random access — supported, unlike list

Use deque when you need fast insertion/removal at both ends (a sliding window, a work queue) but still want random access — use vector when you only ever grow at the back, since it has better cache locality (one contiguous block vs. chunked blocks).

When Is list Actually the Right Choice? Almost never, in practice — its O(1) insertion advantage is usually outweighed by terrible cache locality (each node is a separate heap allocation scattered in memory). Reach for list only when you need to splice large chunks of elements between containers in O(1) (splice()), or need iterator stability across insertions/removals anywhere in the sequence while also holding long-lived iterators to specific elements.

Multithreading vs Multiprocessing

Multithreading means running multiple threads inside one process, sharing its memory. Multiprocessing means running multiple independent processes, each with its own memory, usually communicating through IPC. Both achieve parallelism; they trade off differently.

multiprocessing_vs_multithreading.cppC++
// MULTITHREADING — one process, multiple threads, shared memory
#include <thread>
int counter = 0;                    // visible to every thread directly — no IPC needed
void increment() { counter++; }     // (needs synchronisation in real code — see next section)
std::thread t(increment);
t.join();

// MULTIPROCESSING — separate processes, no shared memory, POSIX example
#include <unistd.h>       // POSIX only — NOT part of standard C++, NOT portable to Windows
#include <sys/wait.h>

pid_t pid = fork();               // clones the CURRENT process into a near-identical child
if (pid == 0) {
    // This block runs in the CHILD process only.
    // It has its OWN COPY of every variable — changes here are invisible to the parent.
    counter = 99;
    _exit(0);
} else {
    // This block runs in the PARENT process only. 'pid' is the child's process ID.
    waitpid(pid, nullptr, 0);  // wait for the child to finish
    // counter is STILL 0 here — the child's change never crossed the process boundary
}
🔴
C++ Has No Standard Multiprocessing Library Unlike Python's built-in multiprocessing module, the C++ standard library has no portable way to spawn a new OS process — std::thread is exclusively about threads within one process. Creating new processes is always OS-specific: fork()/exec() on POSIX (Linux/macOS), CreateProcess on Windows, or a third-party cross-platform library. This is a common point of confusion for people coming from languages with a built-in multiprocessing API.
ChooseWhen
MultithreadingTasks need to share large in-memory data structures and communicate frequently; you're CPU-bound and want to avoid IPC overhead; you accept that one bad thread can crash the whole program.
MultiprocessingYou need fault isolation (a worker crashing shouldn't take down the whole system); tasks are largely independent; you want to bypass a language runtime's global lock (e.g. Python's GIL — not a C++ concern, but a common reason people reach for it); you're distributing work across machines anyway.

Condition Variables — Producer-Consumer

condition_variable.cpp C++ 
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <queue>

std::queue<int>       data_queue;
std::mutex              mtx;
std::condition_variable cv;
bool                    done = false;

void producer() {
    for (int i = 1; i <= 5; ++i) {
        {
            std::lock_guard<std::mutex> lk(mtx);
            data_queue.push(i);
            std::cout << "Produced: " << i << "\n";
        }
        cv.notify_one();
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
    }
    {
        std::lock_guard<std::mutex> lk(mtx);
        done = true;
    }
    cv.notify_all();
}

void consumer() {
    while (true) {
        std::unique_lock<std::mutex> lk(mtx);
        // Lambda guards against spurious wakeups
        cv.wait(lk, []{ return !data_queue.empty() || done; });
        while (!data_queue.empty()) {
            std::cout << "Consumed: " << data_queue.front() << "\n";
            data_queue.pop();
        }
        if (done) break;
    }
}

int main() {
    std::thread p(producer);
    std::thread c(consumer);
    p.join(); c.join();
    std::cout << "Done\n";
    return 0;
}

lock_guard vs unique_lock vs scoped_lock — Complete Comparison

All three are RAII wrappers that lock a mutex on construction and unlock it on destruction — but they differ in flexibility, and picking the wrong one either wastes performance or removes a capability you actually needed.

std::lock_guard — The Minimal, Zero-Overhead Option

lock_guard_usage.cppC++
#include <mutex>
#include <iostream>

std::mutex mtx;
int counter = 0;

void increment() {
    std::lock_guard<std::mutex> lock(mtx);   // locks HERE, unconditionally, immediately
    ++counter;
}   // unlocks HERE, when lock goes out of scope — no other option exists

int main() {
    for (int i = 0; i < 1000; ++i) increment();
    std::cout << "counter = " << counter << "\n";
    return 0;
}
Expected Output
counter = 1000

lock_guard cannot be unlocked early, cannot be default-constructed, and cannot be moved — it does exactly one thing (lock now, unlock at scope end) with zero extra bookkeeping, which makes it the cheapest option and the right default when you don't need anything fancier.

std::unique_lock — The Flexible Option

unique_lock_usage.cppC++
#include <mutex>
#include <iostream>

std::mutex mtx;

void doWork() {
    std::unique_lock<std::mutex> lock(mtx);   // locked
    std::cout << "Critical section 1\n";

    lock.unlock();                       // manually unlock EARLY — lock_guard cannot do this
    std::cout << "Doing non-critical work, unlocked\n";

    lock.lock();                         // manually re-lock — also impossible with lock_guard
    std::cout << "Critical section 2\n";
}   // destructor unlocks automatically IF still locked (it is, here)

int main() {
    std::unique_lock<std::mutex> deferred(mtx, std::defer_lock);  // constructed WITHOUT locking
    std::cout << std::boolalpha << "owns lock yet? " << deferred.owns_lock() << "\n";  // false
    deferred.lock();
    std::cout << "owns lock now? " << deferred.owns_lock() << "\n";         // true
    deferred.unlock();

    doWork();
    return 0;
}
Expected Output
owns lock yet? false owns lock now? true Critical section 1 Doing non-critical work, unlocked Critical section 2

unique_lock can be locked/unlocked multiple times, constructed without locking (std::defer_lock), moved (but not copied), and is required by std::condition_variable::wait() — recall from the producer/consumer example earlier that cv.wait(lk, predicate) needs to unlock the mutex while waiting and re-lock it on wake-up, which only unique_lock supports. This flexibility costs a small amount of extra bookkeeping compared to lock_guard.

std::scoped_lock — The Multi-Mutex, Deadlock-Free Option (C++17)

scoped_lock_usage.cppC++
#include <mutex>
#include <iostream>
#include <thread>

std::mutex mtxA, mtxB;

void transfer(int from, int to) {
    // Locks BOTH mutexes at once using a deadlock-avoidance algorithm internally —
    // safe even if another thread locks mtxA and mtxB in the opposite order.
    std::scoped_lock lock(mtxA, mtxB);
    std::cout << "Transferring " << from << " -> " << to << "\n";
}   // both mutexes unlocked here, in reverse order

int main() {
    std::thread t1(transfer, 100, 200);
    std::thread t2(transfer, 200, 100);   // opposite order — would deadlock with naive separate locks
    t1.join(); t2.join();
    return 0;
}
Expected Output (order between the two lines may vary)
Transferring 100 -> 200 Transferring 200 -> 100

scoped_lock is essentially lock_guard generalized to accept any number of mutexes at once (including just one), and internally uses the same deadlock-avoidance algorithm as std::lock(). With a single mutex it behaves identically to lock_guard.

std::atomic — Lock-Free Shared State

A mutex protects a critical section by making other threads wait. For a single variable (a counter, a flag), that's often more machinery than necessary — std::atomic<T> makes individual reads, writes, and read-modify-write operations indivisible at the hardware level, with no thread ever blocked waiting for a lock.

atomic_basics.cppC++
#include <iostream>
#include <atomic>
#include <thread>
#include <vector>

std::atomic<int> counter{0};       // safe to increment from many threads, no mutex needed
std::atomic<bool> ready{false};   // classic lock-free "signal" flag

void worker() {
    while (!ready.load()) { /* spin, waiting for the signal */ }
    counter.fetch_add(1);            // atomic read-modify-write — no lost updates, ever
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 10; ++i) threads.emplace_back(worker);

    ready.store(true);         // release all 10 workers at once
    for (auto& t : threads) t.join();

    std::cout << "counter = " << counter.load() << "\n";   // always exactly 10

    // compare_exchange — the building block for lock-free algorithms
    std::atomic<int> value{5};
    int expected = 5;
    bool swapped = value.compare_exchange_strong(expected, 99);
    std::cout << std::boolalpha << "swapped: " << swapped << "  value: " << value.load() << "\n";

    int wrongExpected = 5;   // value is now 99, not 5 — this CAS should fail
    bool swapped2 = value.compare_exchange_strong(wrongExpected, 1);
    std::cout << "swapped2: " << swapped2 << "  wrongExpected now holds: " << wrongExpected << "\n";
    return 0;
}
Expected Output
counter = 10 swapped: true value: 99 swapped2: false wrongExpected now holds: 99

Note the last line: when compare_exchange_strong fails (the current value didn't match expected), it writes the actual current value back into expected — this is exactly what lets lock-free retry loops work: re-read the fresh value and try again without a separate load.

Atomics protect single variables; they are not a general substitute for a mutex-protected critical section spanning multiple pieces of state.

Semaphores — std::counting_semaphore & std::binary_semaphore (C++20)

A mutex is owned by exactly one thread at a time and must be unlocked by that same thread. A semaphore is more general: it holds an internal counter, and any thread can increment (release) or decrement (acquire) it — including a different thread than the one that acquired it. This makes semaphores the right tool for signaling between threads and for limiting concurrent access to a pool of N interchangeable resources, neither of which a mutex expresses naturally.

semaphore_signal.cppC++
#include <iostream>
#include <semaphore>
#include <thread>

std::binary_semaphore signal{0};   // starts at 0 — "not signaled yet"

void waiter() {
    std::cout << "Waiter: waiting for signal...\n";
    signal.acquire();          // BLOCKS here until another thread calls release()
    std::cout << "Waiter: signal received, proceeding!\n";
}

int main() {
    std::thread t(waiter);

    std::this_thread::sleep_for(std::chrono::milliseconds(100));
    std::cout << "Main: doing setup work...\n";
    std::cout << "Main: sending signal\n";
    signal.release();          // wakes up the waiting thread — NOTE: different thread than the one that will acquire again next time

    t.join();
    return 0;
}

Counting Semaphore — Limiting Concurrent Access to N Resources

counting_semaphore.cppC++
#include <iostream>
#include <semaphore>
#include <thread>
#include <vector>
#include <mutex>

std::counting_semaphore<3> pool{3};   // only 3 "slots" available at once — e.g. 3 identical hardware ports
std::mutex printMtx;

void useResource(int id) {
    pool.acquire();                     // takes a slot — BLOCKS if all 3 are already in use
    {
        std::lock_guard<std::mutex> lk(printMtx);
        std::cout << "Thread " << id << " acquired a resource slot\n";
    }
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    pool.release();                     // gives the slot back — ANY waiting thread can take it, not necessarily this one's "owner"
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 6; ++i) threads.emplace_back(useResource, i);
    for (auto& t : threads) t.join();
    std::cout << "All 6 threads completed, never more than 3 ran concurrently\n";
    return 0;
}

recursive_mutex — When the Same Thread Needs to Lock Twice

A regular std::mutex has undefined behaviour if the same thread tries to lock it a second time while already holding it — this is a self-deadlock. A std::recursive_mutex allows the owning thread to lock it multiple times, tracking the lock count. It unlocks fully only when unlock has been called as many times as lock.

recursive_mutex.cppC++
#include <iostream>
#include <mutex>

class SafeCounter {
    int count_ = 0;
    std::recursive_mutex mtx_;   // recursive — same thread may lock multiple times

public:
    void increment() {
        std::lock_guard<std::recursive_mutex> lock(mtx_);
        ++count_;
    }

    // incrementTwice calls increment() while ALREADY holding mtx_.
    // With a regular mutex this would self-deadlock. recursive_mutex permits it.
    void incrementTwice() {
        std::lock_guard<std::recursive_mutex> lock(mtx_);   // lock count: 1
        increment();   // lock count: 2 — same thread, allowed
        increment();   // lock count: 3
    }   // lock_guard destructs: count back to 0 — fully unlocked

    int value() {
        std::lock_guard<std::recursive_mutex> lock(mtx_);
        return count_;
    }
};

int main() {
    SafeCounter c;
    c.incrementTwice();
    c.increment();
    std::cout << "count = " << c.value() << "\n";   // 3
    return 0;
}
Expected Output
count = 3
⚠️
Prefer Refactoring Over recursive_mutex recursive_mutex is heavier than mutex (tracks lock depth). Its need often signals a design issue: a private helper being called from both a public locked method and directly. The cleaner fix is to split the helper into an unlocked internal version called under a lock, and a public version that acquires the lock. Use recursive_mutex only when you genuinely cannot avoid re-entry (e.g. a callback that may be invoked recursively by third-party code).

shared_mutex — Reader-Writer Lock (C++17)

When many threads read shared data and writes are rare, a regular mutex is wasteful — it serialises all readers even though simultaneous reads are safe. A std::shared_mutex (C++17) allows multiple concurrent readers or one exclusive writer, never both simultaneously.

shared_mutex.cppC++
#include <iostream>
#include <shared_mutex>
#include <thread>
#include <vector>
#include <string>

class Config {
    std::string data_ = "initial";
    mutable std::shared_mutex rw_;   // mutable: read methods are const but still lock

public:
    // Read — shared lock: many threads can call this simultaneously
    std::string get() const {
        std::shared_lock lock(rw_);   // C++17 — shared (read) lock
        return data_;
    }

    // Write — exclusive lock: only one thread at a time; blocks all readers
    void set(const std::string& s) {
        std::unique_lock lock(rw_);   // exclusive (write) lock
        data_ = s;
    }
};

int main() {
    Config cfg;
    std::vector<std::thread> readers;

    // Launch 4 readers — they all run concurrently with each other
    for (int i = 0; i < 4; ++i)
        readers.emplace_back([&, i]{
            std::cout << "Reader " << i << ": " << cfg.get() << "\n";
        });

    std::thread writer([&]{ cfg.set("updated"); });   // exclusive

    writer.join();
    for (auto& t : readers) t.join();

    std::cout << "Final: " << cfg.get() << "\n";
    return 0;
}

timed_mutex, try_lock — Non-Blocking & Timeout Locking

Sometimes blocking indefinitely on a lock is unacceptable — a real-time control loop must react within a deadline, and waiting forever for a mutex defeats the purpose. try_lock() returns immediately, and try_lock_for() / try_lock_until() respect a time budget.

timed_mutex.cppC++
#include <iostream>
#include <mutex>
#include <thread>
#include <chrono>
using namespace std::chrono_literals;

std::timed_mutex tmtx;

void workerA() {
    std::lock_guard lock(tmtx);          // holds the lock for 200ms
    std::cout << "A: acquired lock\n";
    std::this_thread::sleep_for(200ms);
    std::cout << "A: releasing\n";
}

void workerB() {
    std::this_thread::sleep_for(10ms);     // let A get in first

    // try_lock — non-blocking: returns true if acquired, false if already held
    if (tmtx.try_lock()) {
        std::cout << "B: try_lock succeeded immediately\n";
        tmtx.unlock();
    } else {
        std::cout << "B: try_lock failed (A still holds it) — doing other work\n";
    }

    // try_lock_for — wait up to 300ms before giving up
    if (tmtx.try_lock_for(300ms)) {
        std::cout << "B: acquired within timeout\n";
        tmtx.unlock();
    } else {
        std::cout << "B: timed out waiting\n";
    }
}

int main() {
    std::thread a(workerA), b(workerB);
    a.join(); b.join();
    return 0;
}
Expected Output
A: acquired lock B: try_lock failed (A still holds it) — doing other work A: releasing B: acquired within timeout

Deadlock Prevention — The Canonical Rules Deadlock requires four conditions simultaneously (Coffman): mutual exclusion, hold-and-wait, no preemption, circular wait. Break the last one: (1) Always acquire multiple mutexes in a consistent global order — or use std::scoped_lock(m1, m2) (C++17), which uses a deadlock-free acquisition algorithm internally. (3) Keep critical sections as short as possible — do not do I/O or heavy computation under a lock.

Lambda Functions

A lambda is an anonymous function object (closure) defined inline. The compiler generates a unique closure class with an operator(). Lambdas capture variables from the enclosing scope and integrate naturally with STL algorithms and async APIs.

Syntax & Capture Modes

lambda_captures.cpp C++ 
#include <iostream>
#include <vector>
#include <algorithm>

int main() {
    int x = 10, y = 20;

    // Capture nothing
    auto l0 = [](int a){ return a * a; };
    std::cout << l0(5) << "\n";  // 25

    // Capture by value [=] — snapshot at lambda creation time
    auto l1 = [=]{ return x + y; };
    x = 99;
    std::cout << l1() << "\n";  // 30 (old x=10, y=20)

    // Capture by reference [&] — sees changes
    int count = 0;
    auto inc = [&count]{ ++count; };
    inc(); inc(); inc();
    std::cout << "count = " << count << "\n";  // 3

    // Mixed capture
    int base = 1000;
    int rate = 5;
    auto calc = [base, &rate](int years) {
        return base + rate * years;
    };
    rate = 10;  // rate captured by ref, so this matters
    std::cout << calc(3) << "\n";  // 1000 + 10*3 = 1030

    // mutable — modify value captures
    int val = 0;
    auto mut = [val]() mutable {
        ++val;  // local copy, doesn't affect outer val
        return val;
    };
    std::cout << mut() << " " << mut() << "\n";  // 1 2
    std::cout << "outer val = " << val << "\n";  // 0

    // Capture this in a class method
    return 0;
}
Expected Output
25 30 count = 3 1030 1 2 outer val = 0

Modern C++ Essentials

Modern C++ isn't a separate language — it's a set of tools that let you express intent more precisely and let the compiler catch more mistakes. This section covers the features every professional codebase from C++11 through C++20 now assumes you know.

auto & decltype

auto deduces a variable's type from its initializer at compile time — it is not dynamic typing, the type is fixed forever once deduced. decltype inspects the declared type of an expression without evaluating it, most useful in generic code and trailing return types.

auto_decltype.cppC++
auto x = 42;              // int
auto y = 3.14;            // double
auto s = std::string("hi"); // std::string, NOT const char*
auto& ref = x;           // int& — auto strips references/const unless you add them back
const auto& cref = x;    // const int&

// decltype preserves EXACT type, including references
int a = 1; int& ra = a;
decltype(ra) rb = a;         // int&  (decltype(ra) is int&, unlike auto)

// Trailing return type — needed when return type depends on template params
template<typename T, typename U>
auto add(T t, U u) -> decltype(t + u) { return t + u; }
// C++14+: just "auto add(T t, U u) { return t + u; }" — return type deduced
⚠️
auto Silently Drops Qualifiers const std::string& getName(); then auto n = getName(); makes n a brand-new std::string copy, not a reference — the const& is stripped. If you meant to bind a reference, write const auto& n = getName(); explicitly.

constexpr, consteval & constinit

These three control when computation happens. constexpr means "can run at compile time if the inputs allow it" — it may still run at runtime. consteval (C++20) means "must always run at compile time," making a true compile-time-only function. constinit (C++20) guarantees a variable is initialized at compile time (no static init order fiasco) while still allowing it to be mutated afterward — unlike constexpr, it doesn't make the variable immutable.

constexpr_family.cppC++
constexpr int factorial(int n) {
    return n <= 1 ? 1 : n * factorial(n - 1);
}
constexpr int f5 = factorial(5);     // computed at COMPILE time -> 120 baked into the binary
int n = readFromUser();
int fn = factorial(n);         // same function, runs at RUNTIME here (n not known at compile time)

consteval int square(int n) { return n * n; }
constexpr int s = square(5);       // OK — compile time
// int bad = square(n);           // ERROR: consteval REQUIRES a compile-time constant arg

constinit static int counter = 0;  // guaranteed compile-time init, but mutable
void tick() { ++counter; }         // legal — constinit != const

Move Semantics, Perfect Forwarding & Forwarding References

An rvalue is a temporary with no name others can refer to — safe to "steal" resources from. std::move doesn't move anything itself; it's just a cast that says "treat this as an rvalue," enabling the move constructor/assignment overload to be selected.

perfect_forwarding.cppC++
template<typename T>
void wrapper(T&& arg) {           // T&& here is a FORWARDING reference (not rvalue ref!)
    target(std::forward<T>(arg)); // preserves arg's original value category
}
// wrapper(x)              -> T deduced as X&  -> forwards as lvalue
// wrapper(std::move(x))   -> T deduced as X   -> forwards as rvalue

// Classic use: emplace_back constructs in-place, forwarding ctor args exactly
std::vector<std::string> v;
v.emplace_back(5, 'x');   // forwards (5,'x') to std::string(size_t, char) — no temporary built first
🔴
Forwarding Reference ≠ Rvalue Reference T&& is a forwarding (universal) reference only when T is a deduced template parameter. void f(std::string&& s) is a plain rvalue reference — no deduction, no forwarding. Confusing the two is one of the most common "why doesn't my template compile like the non-template version" bugs.

Data Structures & Algorithms — The Core Six

This module steps outside pure C++ language mechanics and into the data structures that every FAANG/MAANG, Microsoft, Apple, and KLA interview loop is built around. 1. Stack — LIFO (Last In, First Out)

Picture a stack of plates in a cafeteria. You can only take the plate sitting on top, and you can only add a new plate to the top. You physically cannot reach into the middle of the stack without first removing everything above it. That single rule — only the top is reachable — is the entire definition of a stack.

Formally, a stack is a linear data structure where insertion and removal both happen at the same end, called the top. The last element pushed is always the first one popped.

Building a Stack From Scratch (Array-Backed)

Before reaching for std::stack, it's worth building one yourself once — this is exactly what interviewers sometimes ask for, and it removes any mystery about what's happening underneath.

stack_from_scratch.cppC++
#include <iostream>
#include <stdexcept>

class MyStack {
    int* data_;
    int top_;       // index of the top element, -1 means empty
    int capacity_;
public:
    explicit MyStack(int capacity)
        : data_(new int[capacity]), top_(-1), capacity_(capacity) {}

    ~MyStack() { delete[] data_; }

    bool isEmpty() const { return top_ == -1; }
    bool isFull()  const { return top_ == capacity_ - 1; }

    void push(int val) {
        if (isFull()) throw std::overflow_error("Stack overflow");
        data_[++top_] = val;      // increment top FIRST, then write
    }

    int pop() {
        if (isEmpty()) throw std::underflow_error("Stack underflow");
        return data_[top_--];      // read the top, THEN decrement
    }

    int peek() const {
        if (isEmpty()) throw std::underflow_error("Stack is empty");
        return data_[top_];       // look, but don't remove
    }

    int size() const { return top_ + 1; }
};

int main() {
    MyStack s(5);
    std::cout << std::boolalpha;
    std::cout << "isEmpty: " << s.isEmpty() << "\n";

    s.push(10); s.push(20); s.push(30);
    std::cout << "size: "  << s.size()   << "\n";
    std::cout << "peek: "  << s.peek()   << "\n";

    std::cout << "pop: " << s.pop() << "\n";
    std::cout << "pop: " << s.pop() << "\n";
    std::cout << "size after 2 pops: " << s.size() << "\n";
    std::cout << "isEmpty: " << s.isEmpty() << "\n";
    return 0;
}
Expected Output
isEmpty: true size: 3 peek: 30 pop: 30 pop: 20 size after 2 pops: 1 isEmpty: false

Real-World Use Case 1 — Balanced Parentheses (Compiler/Parser Logic)

This is the single most common stack interview question, because it's a direct simplification of what a real compiler does when parsing nested syntax (brackets, function calls, XML/HTML tags).

balanced_parens.cppC++
#include <iostream>
#include <stack>
#include <string>

bool isBalanced(const std::string& expr) {
    std::stack<char> st;
    for (char c : expr) {
        if (c == '(' || c == '[' || c == '{') {
            st.push(c);
        } else if (c == ')' || c == ']' || c == '}') {
            if (st.empty()) return false;         // closing with nothing open
            char top = st.top(); st.pop();
            if ((c == ')' && top != '(') ||
                (c == ']' && top != '[') ||
                (c == '}' && top != '{'))
                return false;                        // wrong type of bracket
        }
    }
    return st.empty();                          // anything left open? not balanced
}

int main() {
    std::cout << std::boolalpha;
    std::cout << isBalanced("{[()()]}") << "\n";  // true
    std::cout << isBalanced("([)]")     << "\n";  // false — wrong nesting
    std::cout << isBalanced("(((")      << "\n";  // false — unclosed
    return 0;
}
Expected Output
true false false

Real-World Use Case 2 — Undo/Redo

Every text editor's undo stack works identically to the code above: each action gets pushed onto an "undo stack" as it happens. Pressing Ctrl+Z pops the most recent action and reverses it — usually pushing the reverse operation onto a separate "redo stack" in the process.

Real-World Use Case 3 — The Function Call Stack (Why Recursion Overflows)

Every time a function calls another function, the runtime pushes a stack frame containing that function's local variables and return address. When the function returns, its frame is popped. This is why deep, unbounded recursion crashes with a "stack overflow" — you are literally exceeding the fixed-size memory region reserved for the call stack.

call_stack_demo.cppC++
#include <iostream>

void countdown(int n) {
    std::cout << "Entering countdown(" << n << ")  [frame pushed]\n";
    if (n > 0) countdown(n - 1);
    std::cout << "Leaving countdown("  << n << ")  [frame popped]\n";
}

int main() {
    countdown(3);
    return 0;
}
Expected Output

Notice the perfect LIFO mirror: the deepest call (countdown(0)) is the first to finish and return — exactly like popping the last plate you put on.

🧠
Memory Trick "Stack = plates. Last plate on, first plate off." Whenever a problem mentions "most recent," "nested," "matching pairs," "undo," or "reverse order" — reach for a stack.

Common Pitfall Calling top() or pop() on an empty std::stack is undefined behavior — it will not throw. Always check empty() first. Also remember std::stack::pop() returns void; you must call top() before pop() if you need the value.

2. Queue — FIFO (First In, First Out)

A queue behaves exactly like a line at a ticket counter: the first person to join the line is the first person served, and new arrivals always join at the back. Insertion happens at the rear; removal happens at the front.

Building a Circular Queue From Scratch

A naive array queue wastes space — once you dequeue from the front, that slot is never reused. A circular queue fixes this by wrapping the index around using the modulo operator, reusing freed slots instead of leaving them empty.

circular_queue.cppC++
#include <iostream>
#include <stdexcept>

class CircularQueue {
    int* data_;
    int front_, rear_, count_, capacity_;
public:
    explicit CircularQueue(int cap)
        : data_(new int[cap]), front_(0), rear_(-1), count_(0), capacity_(cap) {}
    ~CircularQueue() { delete[] data_; }

    bool isEmpty() const { return count_ == 0; }
    bool isFull()  const { return count_ == capacity_; }

    void enqueue(int val) {
        if (isFull()) throw std::overflow_error("Queue is full");
        rear_ = (rear_ + 1) % capacity_;   // wrap around!
        data_[rear_] = val;
        ++count_;
    }

    int dequeue() {
        if (isEmpty()) throw std::underflow_error("Queue is empty");
        int val = data_[front_];
        front_ = (front_ + 1) % capacity_;  // wrap around!
        --count_;
        return val;
    }

    int front() const {
        if (isEmpty()) throw std::underflow_error("Queue is empty");
        return data_[front_];
    }
    int size() const { return count_; }
};

int main() {
    CircularQueue q(3);
    q.enqueue(10); q.enqueue(20); q.enqueue(30);
    std::cout << "front: " << q.front() << "  size: " << q.size() << "\n";

    std::cout << "dequeue: " << q.dequeue() << "\n";  // 10 — frees a slot
    q.enqueue(40);   // reuses the freed slot via wraparound — would fail in a naive array queue
    std::cout << "size after reuse: " << q.size() << "\n";

    while (!q.isEmpty())
        std::cout << "dequeue: " << q.dequeue() << "\n";
    return 0;
}

Real-World Use Case — BFS (Breadth-First Search)

BFS explores a graph or tree level by level. A queue is what enforces this ordering: nodes are visited in exactly the order they were discovered, guaranteeing the shortest path is found first in an unweighted graph.

bfs_graph.cppC++
#include <iostream>
#include <queue>
#include <vector>
#include <unordered_set>

void bfs(int start, const std::vector<std::vector<int>>& adj) {
    std::queue<int> q;
    std::unordered_set<int> visited;

    q.push(start);
    visited.insert(start);

    while (!q.empty()) {
        int node = q.front(); q.pop();
        std::cout << "Visit: " << node << "\n";

        for (int neighbor : adj[node]) {
            if (!visited.count(neighbor)) {
                visited.insert(neighbor);
                q.push(neighbor);   // discovered now, processed later — FIFO order
            }
        }
    }
}

int main() {
    // Graph: 0-1, 0-2, 1-3, 2-3, 3-4
    std::vector<std::vector<int>> adj = {
        {1, 2}, {0, 3}, {0, 3}, {1, 2, 4}, {3}
    };
    bfs(0, adj);
    return 0;
}

        delete head;
        return nullptr;

    Node* slow = head;
    Node* fast = head;
    Node* prev = nullptr; // Tracks the node right before 'slow'

    // Move fast by 2 steps and slow by 1 step
    while (fast != nullptr && fast->next != nullptr) {
        prev = slow;
        slow = slow->next;
        fast = fast->next->next;
    }

    // 'slow' is now pointing to the exact middle node
    // 'prev' is pointing to the node before it
    prev->next = slow->next; // Bypass the middle node
    delete slow;             // Free the memory

    return head;
}

Doubly Linked List — Bidirectional Traversal

A doubly linked list adds a prev pointer to each node, at the cost of extra memory per node. This enables O(1) backward traversal and O(1) deletion of a node when you already hold a pointer to it — no need to walk from the head to find its predecessor.

    std::cout << "\n";

    while (tail->next) tail = tail->next;

    std::cout << "Backward: ";
    for (DNode* cur = tail; cur; cur = cur->prev) std::cout << cur->val << " ";
    std::cout << "\n";

    return 0;

Circular Linked List

In a circular linked list, the last node points back to the first instead of to nullptr. There is no natural "end" — traversal must stop based on a count or by detecting you've returned to the starting node. This shape underlies round-robin CPU scheduling, where the "next process" always wraps back to the front of the queue of processes.

circular_linked_list.cppC++
#include <iostream>

struct CNode { int val; CNode* next; CNode(int v):val(v),next(nullptr){} };

    for (int i = 0; i < 6; ++i) {     // walk around the circle twice

        cur = cur->next;

5. Max Heap / Min Heap

Think of a hospital emergency room: patients aren't seen in arrival order — the most critical patient is always seen next. A heap guarantees the same thing: the "most important" element (maximum or minimum) always sits at the root, instantly accessible.

A heap is a complete binary tree (filled left to right, no gaps) satisfying the heap property: in a max heap, every parent ≥ its children; in a min heap, every parent ≤ its children. Note this does not mean the whole thing is sorted — only the parent-child relationship is guaranteed.

Array Representation

Because a heap is always a complete tree, it can be stored in a plain array with no pointers at all. For a node at index i: left child = 2i+1, right child = 2i+2, parent = (i-1)/2.

           50  (index 0)
         /    \
       30      40   (indices 1, 2)
      /  \    /
    10   20  35     (indices 3, 4, 5)

Parent of index 4 (20) = (4-1)/2 = 1 -> value 30. Correct: 30 >= 20. ✓

Full Max-Heap Implementation — Insert, Extract, Heapify

max_heap.cppC++
#include <iostream>
#include <vector>
#include <stdexcept>

class MaxHeap {
    std::vector<int> data_;

    int parent(int i) { return (i - 1) / 2; }
    int left(int i)   { return 2*i + 1; }
    int right(int i)  { return 2*i + 2; }

    // Bubble UP — fixes the heap after an insertion at the end
    void heapifyUp(int i) {
        while (i > 0 && data_[parent(i)] < data_[i]) {
            std::swap(data_[i], data_[parent(i)]);
            i = parent(i);
        }
    }

    // Bubble DOWN — fixes the heap after removing the root
    void heapifyDown(int i) {
        int largest = i, l = left(i), r = right(i);
        int n = data_.size();
        if (l < n && data_[l] > data_[largest]) largest = l;
        if (r < n && data_[r] > data_[largest]) largest = r;
        if (largest != i) {
            std::swap(data_[i], data_[largest]);
            heapifyDown(largest);
        }
    }

public:
    void insert(int val) {
        data_.push_back(val);              // add at the end
        heapifyUp(data_.size() - 1); // then bubble it up to the right spot
    }

    int extractMax() {
        if (data_.empty()) throw std::underflow_error("Heap is empty");
        int maxVal = data_[0];
        data_[0] = data_.back();          // move last element to root
        data_.pop_back();
        if (!data_.empty()) heapifyDown(0);   // restore heap property
        return maxVal;
    }

    int peek() const { return data_.front(); }
    bool empty() const { return data_.empty(); }
};

int main() {
    MaxHeap heap;
    for (int v : {10, 50, 30, 70, 20})
        heap.insert(v);

    std::cout << "Peek (max): " << heap.peek() << "\n";

    std::cout << "Extracting in order: ";
    while (!heap.empty())
        std::cout << heap.extractMax() << " ";
    std::cout << "\n";
    return 0;
}

Heap Sort — Sorting Using the Heap Property

Build a max heap from the array, then repeatedly swap the root (the current maximum) with the last unsorted element and shrink the heap by one. This sorts the array in place.

heap_sort.cppC++
#include <iostream>
#include <vector>

void heapifyDown(std::vector<int>& arr, int n, int i) {
    int largest = i, l = 2*i+1, r = 2*i+2;
    if (l < n && arr[l] > arr[largest]) largest = l;
    if (r < n && arr[r] > arr[largest]) largest = r;
    if (largest != i) {
        std::swap(arr[i], arr[largest]);
        heapifyDown(arr, n, largest);
    }
}

void heapSort(std::vector<int>& arr) {
    int n = arr.size();
    // Build max heap — start from the last non-leaf node, O(n) overall
    for (int i = n/2 - 1; i >= 0; --i)
        heapifyDown(arr, n, i);

    // Repeatedly move the max to the end, shrink, and re-heapify
    for (int i = n - 1; i > 0; --i) {
        std::swap(arr[0], arr[i]);
        heapifyDown(arr, i, 0);
    }
}

int main() {
    std::vector<int> arr = {12, 11, 13, 5, 6, 7};
    heapSort(arr);
    for (int x : arr) std::cout << x << " ";
    std::cout << "\n";
    return 0;
}
Expected Output
5 6 7 11 12 13

  • Priority scheduling — OS process schedulers pick the highest-priority ready task next.
  • Kth largest/smallest element — maintain a heap of size K instead of sorting the whole dataset (O(n log k) instead of O(n log n)).

6. Priority Queue

A priority queue is the same emergency-room idea as a heap, wearing a different name tag: it's the abstract concept ("serve by priority, not by arrival order"), and a heap is simply the most common, most efficient way to implement that concept. In C++, std::priority_queue is a container adapter built directly on top of a heap.

Basic Usage — Max and Min Priority Queues

priority_queue_basics.cppC++
#include <iostream>
#include <queue>
#include <vector>

int main() {
    // Max-heap by default — largest priority served first
    std::priority_queue<int> maxPQ;
    maxPQ.push(10); maxPQ.push(50); maxPQ.push(30);
    std::cout << "Max PQ top: " << maxPQ.top() << "\n";   // 50
    maxPQ.pop();
    std::cout << "Max PQ top after pop: " << maxPQ.top() << "\n"; // 30

    // Min-heap version — explicitly specify std::greater as the comparator
    std::priority_queue<int, std::vector<int>, std::greater<int>> minPQ;
    minPQ.push(10); minPQ.push(50); minPQ.push(30);
    std::cout << "Min PQ top: " << minPQ.top() << "\n";   // 10
    return 0;
}
Expected Output
Max PQ top: 50 Max PQ top after pop: 30 Min PQ top: 10

Custom Priority — Priority Queue of Objects

Real scheduling systems rarely prioritize plain integers — they prioritize tasks or events with their own comparison logic, provided via a custom comparator.

priority_queue_custom.cppC++
#include <iostream>
#include <queue>
#include <string>

struct Task {
    std::string name;
    int urgency;   // higher = more urgent
};

// Comparator: priority_queue calls this to decide ordering.
// Returning true means "a has LOWER priority than b" (so b comes out first)
struct CompareTask {
    bool operator()(const Task& a, const Task& b) {
        return a.urgency < b.urgency;
    }
};

int main() {
    std::priority_queue<Task, std::vector<Task>, CompareTask> tasks;
    tasks.push({"Fix typo", 1});
    tasks.push({"Server down!", 10});
    tasks.push({"Update docs", 2});

    while (!tasks.empty()) {
        std::cout << tasks.top().name << " (urgency " << tasks.top().urgency << ")\n";
        tasks.pop();
    }
    return 0;
}
Expected Output
Server down! (urgency 10) Update docs (urgency 2) Fix typo (urgency 1)

Classic Interview Problem — Kth Largest Element

kth_largest.cppC++
#include <iostream>
#include <queue>
#include <vector>

int findKthLargest(std::vector<int>& nums, int k) {
    // Keep a MIN-heap of size k — its root is always the k-th largest so far
    std::priority_queue<int, std::vector<int>, std::greater<int>> minHeap;
    for (int n : nums) {
        minHeap.push(n);
        if ((int)minHeap.size() > k) minHeap.pop();  // discard the smallest of the top-k
    }
    return minHeap.top();
}

int main() {
    std::vector<int> nums = {3, 2, 1, 5, 6, 4};
    std::cout << "2nd largest: " << findKthLargest(nums, 2) << "\n";  // 5
    return 0;
}
Expected Output
2nd largest: 5

Why a min-heap for "Kth largest"? Counterintuitive but key: keeping the smallest of your current top-k candidates at the root lets you cheaply discard anything smaller the moment a bigger candidate arrives. Time: O(n log k) — far better than sorting the entire array (O(n log n)) when k is small.

Real-World Use Cases — Why Companies Ask This

  • Dijkstra's Shortest Path — always expand the closest unvisited node next; a priority queue makes this O(E log V) instead of O(V²).
  • Huffman Encoding (data compression) — repeatedly combine the two least-frequent symbols; a min priority queue drives the entire algorithm.
  • Task/job schedulers — Kubernetes pod scheduling and OS process schedulers prioritize by urgency or resource weight, not arrival order.
  • A* pathfinding (games, maps) — orders candidate nodes by estimated total cost to the goal.

Interviewers ask these questions specifically to see whether you reach for a heap-based O(log n)-per-operation solution instead of defaulting to a full O(n log n) sort when only the top-K or single next-priority element is actually needed.

🧠
Memory Trick "Priority Queue = VIP line — doesn't matter when you arrived, priority wins." If a problem says "Kth largest," "most frequent," "shortest path," or "always process the most/least important next" — reach for a priority queue.
⚠️
Common Pitfall Sorting the entire dataset when only the top-K element or the single next-priority item is actually needed. This turns an O(n log k) solution into an unnecessary O(n log n) one — interviewers specifically probe for this optimization when they ask "can you do better?"

Design Patterns

Design patterns are reusable solutions to problems that show up over and over in object-oriented software. They aren't C++-specific syntax — they're shapes for your code that other engineers instantly recognize, which is exactly why interviewers probe them: a candidate who reaches for the right pattern shows they can structure a system, not just write working statements.

1. Singleton Pattern

A Singleton guarantees a class has exactly one instance for the lifetime of the program, with one global access point to it. It's used for things that are genuinely singular by nature: a logger, a configuration manager, a hardware driver for a single physical device.

Your Code, Reviewed

You wrote exactly the modern, correct shape of a Singleton — the "Meyer's Singleton" using a function-local static. Let's walk through it, then look closely at the last line, because it hides a genuine compiler error that's worth understanding.

singleton.cppC++
#include <iostream>
using namespace std;

class Singleton
{
    private:
    int data;
    Singleton() : data(0) {}        // private constructor — nobody outside can "new" one

    public:
    Singleton(const Singleton&) = delete;             // no copying
    Singleton& operator=(const Singleton&) = delete;  // no copy-assigning
    Singleton(Singleton&&) = delete;                  // no moving
    Singleton& operator=(Singleton&&) = delete;       // no move-assigning

    static Singleton& getInstance()
    {
        static Singleton instance;    // constructed on FIRST call only, thread-safe since C++11
        return instance;
    }
    void setData(int data1) { data = data1; }
    void doSomething() { cout << "Data: " << data << endl; }
};

int main()
{
    Singleton& s1 = Singleton::getInstance();
    s1.setData(10);
    Singleton& s2 = Singleton::getInstance();
    s1.doSomething();
    s2 = move(s1);   // ← compiler error — see below
    return 0;
}
Actual Compiler Output
error: use of deleted function 'Singleton& Singleton::operator=(Singleton&&)' s2 = move(s1); ^ note: 'Singleton& Singleton::operator=(Singleton&&)' explicitly deleted here
🔴
Why This Line Fails — And Why That's Correct You explicitly deleted the move-assignment operator (correctly — a Singleton must never be reassignable, moved-from, or moved-into; there is only ever one, and letting it be "moved" would either leave it in a moved-from state or silently create a second logical instance). s2 = move(s1) tries to call exactly that deleted operator. The fix isn't to restore move-assignment — it's to delete that last line. Since getInstance() always returns a reference to the same object, s1 and s2 already refer to the identical instance; there is nothing to move. This is actually a great instinct check: a Singleton that compiles with a move or copy anywhere in the call chain has a design leak somewhere.

Removing that line gives you working, idiomatic output:

Corrected Program Output
Data: 10

Why static Singleton instance; Inside a Function Is Special

This is called a function-local static, and it's the modern preferred way to write a Singleton in C++11 and later, for one specific reason: the C++11 standard guarantees that initialization of a function-local static is thread-safe — if two threads call getInstance() for the first time simultaneously, the language guarantees only one of them actually constructs instance, and the other blocks until it's ready. This is sometimes called "magic statics." Before C++11, this required manual double-checked locking with a mutex — the modern version needs none of that.

singleton_thread_safety.cppC++
#include <iostream>
#include <thread>
#include <vector>

class Logger {
    Logger() { std::cout << "Logger constructed (should print ONCE)\n"; }
public:
    Logger(const Logger&) = delete;
    Logger& operator=(const Logger&) = delete;

    static Logger& instance() {
        static Logger logger;   // C++11 guarantees exactly-once, thread-safe init
        return logger;
    }
    void log(const std::string& msg) { std::cout << "[LOG] " << msg << "\n"; }
};

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 5; ++i)
        threads.emplace_back([i]{ Logger::instance().log("from thread " + std::to_string(i)); });
    for (auto& t : threads) t.join();
    return 0;
}
Expected Output (order of log lines may vary, constructor always once)
Logger constructed (should print ONCE) [LOG] from thread 0 [LOG] from thread 1 [LOG] from thread 2 [LOG] from thread 3 [LOG] from thread 4

2. Factory Pattern

A Factory centralizes object creation behind a function or class, so calling code asks for "a Shape" or "a Logger" without knowing — or caring — which concrete class gets instantiated. This decouples the code that uses objects from the code that decides which type to construct.

Full Example — Shape Factory

factory_pattern.cppC++
#include <iostream>
#include <memory>
#include <string>

// The common interface every product implements
class Shape {
public:
    virtual void draw() const = 0;
    virtual ~Shape() = default;
};

class Circle : public Shape {
public:
    void draw() const override { std::cout << "Drawing a Circle\n"; }
};

class Square : public Shape {
public:
    void draw() const override { std::cout << "Drawing a Square\n"; }
};

class Triangle : public Shape {
public:
    void draw() const override { std::cout << "Drawing a Triangle\n"; }
};

// The Factory — the ONLY place that knows about concrete classes
class ShapeFactory {
public:
    static std::unique_ptr<Shape> create(const std::string& type) {
        if (type == "circle")   return std::make_unique<Circle>();
        if (type == "square")   return std::make_unique<Square>();
        if (type == "triangle") return std::make_unique<Triangle>();
        return nullptr;   // unknown type — caller must check
    }
};

int main() {
    // Calling code never mentions Circle, Square, or Triangle by name
    for (const auto& type : {"circle", "square", "triangle", "hexagon"}) {
        auto shape = ShapeFactory::create(type);
        if (shape) shape->draw();
        else       std::cout << "Unknown shape type: " << type << "\n";
    }
    return 0;
}
Expected Output
Drawing a Circle Drawing a Square Drawing a Triangle Unknown shape type: hexagon

Why This Matters — Adding a New Type Costs Nothing at the Call Site

If you later add a Pentagon class, you only touch ShapeFactory::create. Every existing call site — anywhere in a large codebase — that calls ShapeFactory::create("pentagon") keeps working unmodified. This is the Factory pattern's core value: it isolates the "which concrete class do I build" decision to one place, honoring the Open/Closed Principle (open for extension, closed for modification).

Complexity & Trade-offs

AspectDetail
Object creation timeO(1) — same as calling the constructor directly, plus one string/enum comparison
MemorySame as the underlying object; returning by unique_ptr adds no runtime overhead over a raw pointer
CouplingCallers depend only on the abstract Shape interface, not concrete classes
CostOne extra layer of indirection; the factory itself must be updated for every new product type
💡
Real-World Use Case GUI toolkits use factories to create the correct native widget per OS without the application code knowing whether it's on Windows, macOS, or Linux. Database libraries use factories to construct the right driver/connection object based on a connection string. Parser libraries often use a factory to build the correct AST node type based on a token.

3. Observer Pattern

The Observer pattern lets one object (the Subject) notify a list of other objects (Observers) automatically whenever its state changes, without the Subject needing to know any details about who those observers are. This is the backbone of event-driven systems: GUI button clicks, publish/subscribe messaging, and — very relevantly — hardware sensor updates broadcasting to multiple subsystems at once.

Full Example — Temperature Sensor Broadcasting to Multiple Listeners

observer_pattern.cppC++
#include <iostream>
#include <vector>
#include <memory>
#include <string>

// Observer interface — anything that wants updates implements this
class IObserver {
public:
    virtual void onUpdate(double temperature) = 0;
    virtual ~IObserver() = default;
};

// The Subject — holds state, and the list of observers to notify
class TemperatureSensor {
    std::vector<IObserver*> observers_;
    double temperature_ = 0.0;
public:
    void attach(IObserver* obs)  { observers_.push_back(obs); }
    void detach(IObserver* obs)  {
        observers_.erase(
            std::remove(observers_.begin(), observers_.end(), obs), observers_.end());
    }

    void setTemperature(double t) {
        temperature_ = t;
        notifyAll();     // state changed — every observer finds out automatically
    }

private:
    void notifyAll() {
        for (auto* obs : observers_) obs->onUpdate(temperature_);
    }
};

// Concrete observers — each reacts differently to the same event
class Display : public IObserver {
public:
    void onUpdate(double temperature) override {
        std::cout << "[Display] Showing temperature: " << temperature << "°C\n";
    }
};

class OverheatAlarm : public IObserver {
public:
    void onUpdate(double temperature) override {
        if (temperature > 80.0)
            std::cout << "[OverheatAlarm] WARNING: temperature critical!\n";
    }
};

class Logger : public IObserver {
public:
    void onUpdate(double temperature) override {
        std::cout << "[Logger] Recorded reading: " << temperature << "\n";
    }
};

int main() {
    TemperatureSensor sensor;

    Display display;
    OverheatAlarm alarm;
    Logger logger;

    sensor.attach(&display);
    sensor.attach(&alarm);
    sensor.attach(&logger);

    std::cout << "--- Setting temperature to 45.0 ---\n";
    sensor.setTemperature(45.0);

    std::cout << "--- Setting temperature to 92.5 ---\n";
    sensor.setTemperature(92.5);

    sensor.detach(&alarm);   // alarm stops receiving updates
    std::cout << "--- Alarm detached. Setting temperature to 99.0 ---\n";
    sensor.setTemperature(99.0);

    return 0;
}
Expected Output
--- Setting temperature to 45.0 --- [Display] Showing temperature: 45°C [Logger] Recorded reading: 45 --- Setting temperature to 92.5 --- [Display] Showing temperature: 92.5°C [OverheatAlarm] WARNING: temperature critical! [Logger] Recorded reading: 92.5 --- Alarm detached. Setting temperature to 99.0 --- [Display] Showing temperature: 99°C [Logger] Recorded reading: 99

Modern C++ Variant — Observer via std::function

In modern C++, you don't need an abstract IObserver interface at all — a vector of std::function callbacks achieves the same decoupling with less boilerplate, and lets you attach lambdas directly.

observer_with_std_function.cppC++
#include <iostream>
#include <vector>
#include <functional>

class Button {
    std::vector<std::function<void()>> onClickListeners_;
public:
    void onClick(std::function<void()> callback) {
        onClickListeners_.push_back(std::move(callback));
    }
    void click() {
        for (auto& listener : onClickListeners_) listener();
    }
};

int main() {
    Button saveButton;
    int clickCount = 0;

    saveButton.onClick([]{ std::cout << "Saving file...\n"; });
    saveButton.onClick([&clickCount]{ ++clickCount; std::cout << "Click count: " << clickCount << "\n"; });

    saveButton.click();
    saveButton.click();
    return 0;
}

In control systems, a sensor broadcasting a reading to a display, a logger, and a safety monitor simultaneously — without the sensor knowing any of them exist — is the exact shape shown above.

4. Strategy Pattern

The Strategy pattern defines a family of algorithms, encapsulates each one in its own class, and makes them interchangeable at runtime. The client code works through an abstract interface — it doesn't know or care which concrete strategy is active. This is the "open for extension, closed for modification" principle in its most direct form.

Real examples: a sorter that can use quicksort, mergesort, or timsort selected at runtime; a payment processor that routes to Stripe, PayPal, or bank transfer; a navigation app that switches between "fastest", "shortest", or "avoid tolls" routes.

strategy_pattern.cppC++
#include <iostream>
#include <memory>
#include <vector>
#include <algorithm>

// ── Strategy interface ───────────────────────────────────────────────────
class ISortStrategy {
public:
    virtual void sort(std::vector<int>& data) const = 0;
    virtual std::string name() const = 0;
    virtual ~ISortStrategy() = default;
};

// ── Concrete strategies — each encapsulates one algorithm ────────────────
class BubbleSort : public ISortStrategy {
public:
    void sort(std::vector<int>& d) const override {
        for (size_t i = 0; i < d.size(); ++i)
            for (size_t j = 0; j + 1 < d.size() - i; ++j)
                if (d[j] > d[j+1]) std::swap(d[j], d[j+1]);
    }
    std::string name() const override { return "BubbleSort (O(n²))"; }
};

class StdSort : public ISortStrategy {
public:
    void sort(std::vector<int>& d) const override { std::sort(d.begin(), d.end()); }
    std::string name() const override { return "std::sort (introsort, O(n log n))"; }
};

// ── Context — works through the interface, unaware of concrete strategy ──
class DataProcessor {
    std::unique_ptr<ISortStrategy> strategy_;
public:
    explicit DataProcessor(std::unique_ptr<ISortStrategy> s)
        : strategy_(std::move(s)) {}

    // swap strategy at runtime — no change to DataProcessor code required
    void setStrategy(std::unique_ptr<ISortStrategy> s) { strategy_ = std::move(s); }

    void process(std::vector<int> data) {
        std::cout << "Using: " << strategy_->name() << "\n";
        strategy_->sort(data);
        for (int v : data) std::cout << v << " ";
        std::cout << "\n";
    }
};

int main() {
    std::vector<int> data = {5, 2, 8, 1, 9, 3};

    DataProcessor proc(std::make_unique<BubbleSort>());

5. Command Pattern

The Command pattern encapsulates a request as an object. This turns an operation (and its parameters) into a first-class value that can be stored, queued, logged, undone, and replayed. A GUI's undo/redo stack, a job queue, and a transactional log are all Command pattern applications.

command_pattern.cppC++
#include <iostream>
#include <memory>
#include <vector>
#include <stack>

// ── Command interface ────────────────────────────────────────────────────
class ICommand {
public:
    virtual void execute() = 0;
    virtual void undo()    = 0;
    virtual ~ICommand()   = default;
};

// ── Receiver — the object that knows how to do the actual work ───────────
class TextEditor {
    std::string text_;
public:
    void append(const std::string& s)    { text_ += s; }
    void removeLast(int n)               { text_ = text_.substr(0, text_.size() - n); }
    const std::string& text() const      { return text_; }
};

// ── Concrete command — bundles receiver + action + undo data ─────────────
class AppendCommand : public ICommand {
    TextEditor& editor_;
    std::string  text_;
public:
    AppendCommand(TextEditor& e, std::string t) : editor_(e), text_(std::move(t)) {}
    void execute() override { editor_.append(text_); }
    void undo()    override { editor_.removeLast(static_cast<int>(text_.size())); }
};

// ── Invoker — stores and executes commands; drives the undo stack ────────
class CommandHistory {
    std::stack<std::unique_ptr<ICommand>> history_;
public:
    void execute(std::unique_ptr<ICommand> cmd) {
        cmd->execute();
        history_.push(std::move(cmd));
    }
    void undo() {
        if (history_.empty()) { std::cout << "Nothing to undo.\n"; return; }
        history_.top()->undo();
        history_.pop();
    }
};

int main() {
    TextEditor     editor;
    CommandHistory history;

    history.execute(std::make_unique<AppendCommand>(editor, "Hello"));
    history.execute(std::make_unique<AppendCommand>(editor, ", World"));
    std::cout << "After 2 appends: \"" << editor.text() << "\"\n";

    history.undo();
    std::cout << "After undo:      \"" << editor.text() << "\"\n";

    history.undo();
    std::cout << "After undo:      \"" << editor.text() << "\"\n";

    history.undo();   // nothing left
    return 0;
}
Expected Output

6. Dependency Injection

Dependency Injection (DI) is not a classical GoF pattern, but it is arguably the most important architectural pattern in production C++. Instead of a class constructing its own dependencies, those dependencies are provided from outside — through a constructor, a setter, or a function parameter. This makes classes:

  • Testable — inject a mock in tests, the real implementation in production
  • Decoupled — the class depends on an interface, not a concrete class
  • Composable — wire different implementations together without touching the class
dependency_injection.cppC++
#include <iostream>
#include <memory>
#include <string>

// ── Abstraction (interface) ────────────────────────────────────────────────
class ILogger {
public:
    virtual void log(const std::string& msg) = 0;
    virtual ~ILogger() = default;
};

// ── Concrete implementations ───────────────────────────────────────────────
class ConsoleLogger : public ILogger {
public:
    void log(const std::string& msg) override {
        std::cout << "[CONSOLE] " << msg << "\n";
    }
};

class SilentLogger : public ILogger {   // used in tests — suppresses all output
public:
    void log(const std::string&) override {}
};

// ── Consumer — receives its dependency through the constructor ─────────────
class PaymentService {
    std::shared_ptr<ILogger> logger_;   // depends on the INTERFACE, not a concrete class
public:
    explicit PaymentService(std::shared_ptr<ILogger> logger)
        : logger_(std::move(logger)) {}

    void pay(double amount) {
        logger_->log("Processing payment: $" + std::to_string(amount));
        // ... real payment logic ...
        logger_->log("Payment complete");
    }
};

int main() {
    // Production: inject the real logger
    PaymentService prod(std::make_shared<ConsoleLogger>());
    prod.pay(99.99);

    std::cout << "\n--- test run (no output expected) ---\n";

    // Test: inject the silent logger — same PaymentService class, no modification needed
    PaymentService test(std::make_shared<SilentLogger>());
    test.pay(0.01);   // runs correctly, produces no console noise during unit tests

    std::cout << "Test run complete (silent logger swallowed output as expected)\n";
    return 0;
}
Expected Output
[CONSOLE] Processing payment: $99.990000 [CONSOLE] Payment complete --- test run (no output expected) --- Test run complete (silent logger swallowed output as expected)

DI vs Singleton — The Core Trade-off A Singleton gives you global access with hidden coupling — any code can silently depend on it, and you cannot swap the implementation in tests without modifying the class itself. Dependency Injection makes every dependency visible in the function signature or constructor, forces you to think about what each class actually needs, and makes swapping implementations (real vs mock, production vs test) trivial. In production C++, DI nearly always produces better-designed, more testable code than the Singleton pattern for the same problem.

7. Decorator Pattern

The Decorator pattern wraps an object inside another object that shares the same interface, adding new behaviour transparently before or after delegating to the wrapped object. It is the composable alternative to subclassing for extending behaviour — you can stack decorators freely at runtime without an exponential explosion of subclasses.

Real examples: a logger that wraps a file writer and adds timestamps; an HTTP middleware chain that wraps a handler adding auth, then compression, then caching; a UI widget that wraps another widget and adds a scrollbar or a border.

The Problem Decorator Solves

Suppose you have a TextRenderer and you need variants: bold, italic, bold+italic, with-border, bold+border, italic+border, bold+italic+border ... Inheritance produces 2N subclasses for N independent features. Decorator produces N small wrapper classes you stack as needed.

decorator_pattern.cppC++
#include <iostream>
#include <memory>
#include <string>

// ── Component interface — shared by concrete component AND all decorators ──
class ITextRenderer {
public:
    virtual std::string render(const std::string& text) const = 0;
    virtual ~ITextRenderer() = default;
};

// ── Concrete component — the base object being decorated ─────────────────
class PlainRenderer : public ITextRenderer {
public:
    std::string render(const std::string& text) const override { return text; }
};

// ── Base decorator — holds a reference to the wrapped component ───────────
class RendererDecorator : public ITextRenderer {
protected:
    std::unique_ptr<ITextRenderer> inner_;    // the wrapped component or another decorator
public:
    explicit RendererDecorator(std::unique_ptr<ITextRenderer> inner)
        : inner_(std::move(inner)) {}
};

// ── Concrete decorator 1: wraps text in **bold markers** ─────────────────
class BoldDecorator : public RendererDecorator {
public:
    using RendererDecorator::RendererDecorator;   // inherit constructor
    std::string render(const std::string& text) const override {
        return "**" + inner_->render(text) + "**";  // delegate, then add bold
    }
};

// ── Concrete decorator 2: wraps text in _italic markers_ ─────────────────
class ItalicDecorator : public RendererDecorator {
public:
    using RendererDecorator::RendererDecorator;
    std::string render(const std::string& text) const override {
        return "_" + inner_->render(text) + "_";
    }
};

// ── Concrete decorator 3: adds a border ──────────────────────────────────
class BorderDecorator : public RendererDecorator {
public:
    using RendererDecorator::RendererDecorator;
    std::string render(const std::string& text) const override {
        return "[ " + inner_->render(text) + " ]";
    }
};

// helper: creates a renderer from a stack of decorators
template<typename Decorator, typename... Rest>
std::unique_ptr<ITextRenderer> make(std::unique_ptr<ITextRenderer> base) {
    return std::make_unique<Decorator>(std::move(base));
}

int main() {
    auto print = [](std::string label, const ITextRenderer& r) {
        std::cout << label << r.render("Hello") << "\n";
    };

    // Plain — no decorators
    print("Plain:              ", PlainRenderer{});

    // Bold only
    print("Bold:               ",
          BoldDecorator(std::make_unique<PlainRenderer>()));

    // Italic + Bold — order matters: outer decorator runs first
    print("Italic(Bold):       ",
          ItalicDecorator(std::make_unique<BoldDecorator>(
              std::make_unique<PlainRenderer>())));

    // Border + Italic + Bold — three layers stacked, zero subclasses
    print("Border(Italic(Bold)): ",
          BorderDecorator(std::make_unique<ItalicDecorator>(
              std::make_unique<BoldDecorator>(
                  std::make_unique<PlainRenderer>()))));
    return 0;
}

Bit Manipulation

Everything so far has worked at the level of objects, containers, and abstractions. Bit manipulation takes you one level down — to the raw 0s and 1s that every variable is actually made of. This is the language you'll speak constantly once you move into embedded systems, because on a microcontroller a single 32-bit register can control dozens of independent hardware features, one bit at a time. Master this module and register-level programming stops looking like magic.

1. The Bitwise Operators

Think of a byte as a row of 8 light switches, each either OFF (0) or ON (1). Bitwise operators let you flip, combine, or inspect those switches directly, without ever touching the switches around them.

bitwise_basics.cppC++
#include <iostream>
#include <bitset>

int main() {
    unsigned char a = 0b00001100;   // 12
    unsigned char b = 0b00001010;   // 10

    std::cout << "a       = " << std::bitset<8>(a) << "\n";
    std::cout << "b       = " << std::bitset<8>(b) << "\n";
    std::cout << "a & b   = " << std::bitset<8>(a & b) << "\n";   // 00001000
    std::cout << "a | b   = " << std::bitset<8>(a | b) << "\n";   // 00001110
    std::cout << "a ^ b   = " << std::bitset<8>(a ^ b) << "\n";   // 00000110
    std::cout << "~a      = " << std::bitset<8>((unsigned char)~a) << "\n"; // 11110011
    std::cout << "a << 2  = " << std::bitset<8>((unsigned char)(a << 2)) << "\n"; // 00110000
    std::cout << "a >> 2  = " << std::bitset<8>(a >> 2) << "\n";   // 00000011
    return 0;
}

2. Setting, Clearing, Toggling, and Checking Bits

These four operations are the entire toolkit you need for register-level programming. Each one follows a fixed idiom built from a mask — a value with 1s in the positions you care about and 0s everywhere else.

bit_operations.cppC++
#include <iostream>
#include <bitset>

int main() {
    uint8_t reg = 0b00000000;   // pretend this is an 8-pin GPIO register

    // ---- SET bit 3 ----
    reg |= (1 << 3);            // OR with mask 00001000 forces bit 3 to 1
    std::cout << "after SET bit 3:    " << std::bitset<8>(reg) << "\n";

    // ---- SET bit 5 too ----
    reg |= (1 << 5);
    std::cout << "after SET bit 5:    " << std::bitset<8>(reg) << "\n";

    // ---- CLEAR bit 3 ----
    reg &= ~(1 << 3);           // AND with mask 11110111 forces bit 3 to 0, leaves rest alone
    std::cout << "after CLEAR bit 3:  " << std::bitset<8>(reg) << "\n";

    // ---- TOGGLE bit 5 ----
    reg ^= (1 << 5);            // XOR flips bit 5, whatever it currently is
    std::cout << "after TOGGLE bit 5: " << std::bitset<8>(reg) << "\n";

    // ---- CHECK bit 5 ----
    bool isSet = reg & (1 << 5);
    std::cout << "is bit 5 set? " << std::boolalpha << isSet << "\n";

    return 0;
}
Expected Output
after SET bit 3: 00001000 after SET bit 5: 00101000 after CLEAR bit 3: 00100000 after TOGGLE bit 5: 00000000 is bit 5 set? false

reg |=  (1 << n);   // SET bit n

Real-world embedded context On an ARM Cortex-M microcontroller, writing GPIOA->ODR |= (1 << 5); sets pin PA5 high (this is literally how the classic "blink an LED" program works) without disturbing pins PA0–PA4 or PA6–PA15 that other parts of your firmware might be driving. Some chips go further and give you separate "set" and "clear" registers (e.g. BSRR on STM32) specifically so that this operation is a single atomic hardware write instead of a read-modify-write — important when an interrupt could sneak in between the read and the write.

3. Bit Masks and Their Applications

A mask is just a number shaped like a stencil. Overlay it on your data with the right operator and only the "cut-out" bits are affected. Masks are how you extract or modify a group of bits at once, not just a single one.

bit_masks.cppC++
#include <iostream>
#include <bitset>

int main() {
    // Imagine a status register: bits 0-2 = error code, bit 3 = busy flag, bits 4-7 = channel ID
    uint8_t status = 0b10110101;

    const uint8_t ERROR_MASK   = 0b00000111;  // lowest 3 bits
    const uint8_t BUSY_MASK    = 0b00001000;  // bit 3
    const uint8_t CHANNEL_MASK = 0b11110000;  // top 4 bits

    uint8_t errorCode = status & ERROR_MASK;                 // extract bits 0-2
    bool    busy      = status & BUSY_MASK;                  // extract bit 3
    uint8_t channel   = (status & CHANNEL_MASK) >> 4;        // extract bits 4-7, shift down to 0-3

    std::cout << "status    = " << std::bitset<8>(status) << "\n";
    std::cout << "errorCode = " << (int)errorCode << "\n";   // 5
    std::cout << "busy      = " << std::boolalpha << busy << "\n"; // true
    std::cout << "channel   = " << (int)channel << "\n";     // 11
    return 0;
}
Expected Output
status = 10110101 errorCode = 5 busy = true channel = 11

Notice the pattern for pulling out a multi-bit field: mask, then shift. Masking with & zeroes out everything you don't want; shifting with >> slides the field you kept down to start at bit 0 so it reads as a normal small integer.

4. Common Interview Patterns

Checking if a number is a power of 2

Any power of 2 has exactly one bit set (1, 2, 4, 8, 16 → 0001, 0010, 0100, 1000...). Subtracting 1 from a power of 2 flips that single bit off and turns every bit below it on, so ANDing the two together always produces zero — and only a power of 2 has that property.

power_of_two.cppC++
#include <iostream>

bool isPowerOfTwo(unsigned int n) {
    return n != 0 && (n & (n - 1)) == 0;
}

int main() {
    for (int n : {1, 2, 3, 4, 15, 16, 1024}) {
        std::cout << n << " -> " << std::boolalpha << isPowerOfTwo(n) << "\n";
    }
}
Expected Output
1 -> true 2 -> true 3 -> false 4 -> true 15 -> false 16 -> true 1024 -> true

Dry run for n = 16 (10000): n − 1 = 15 (01111). 10000 & 01111 = 00000 → zero, so it's a power of 2. Dry run for n = 15 (01111): n − 1 = 14 (01110). 01111 & 01110 = 01110 → non-zero, so it's not.

Swapping two variables without a temp variable

xor_swap.cppC++
#include <iostream>

int main() {
    int a = 5, b = 9;   // 0101, 1001
    a ^= b;             // a = 0101 ^ 1001 = 1100 (12)
    b ^= a;             // b = 1001 ^ 1100 = 0101 (5)  -- original a!
    a ^= b;             // a = 1100 ^ 0101 = 1001 (9)  -- original b!
    std::cout << "a=" << a << " b=" << b << "\n"; // a=9 b=5
    return 0;
}
⚠️
Know it, but don't ship it XOR swap is a classic interview trick, and it's genuinely useful in tight register-only contexts (some CPU ISAs even had an XCHG-free swap idiom baked in). In everyday application code, std::swap(a, b) is clearer, equally fast after optimization, and — unlike the XOR trick — doesn't silently zero both variables if you accidentally call it with a and b being the same variable (a ^= a is always 0).

5. Bit Fields in C++ Structs

A bit field lets you tell the compiler "this member only needs 3 bits, not a whole 32-bit int," so several small fields can be packed together into a single word. This mirrors, in C++ syntax, exactly the kind of packed status register you saw in the masking example above.

bit_fields.cppC++
#include <iostream>
#include <cstdint>

struct StatusRegister {
    uint8_t errorCode : 3;   // uses 3 bits, values 0-7
    uint8_t busy      : 1;   // uses 1 bit, values 0-1
    uint8_t channel   : 4;   // uses 4 bits, values 0-15
};                            // total: 8 bits = fits in exactly 1 byte

int main() {
    std::cout << "sizeof(StatusRegister) = " << sizeof(StatusRegister) << " byte(s)\n";

    StatusRegister sr;
    sr.errorCode = 5;
    sr.busy      = 1;
    sr.channel   = 11;

    std::cout << "errorCode = " << (int)sr.errorCode << "\n";
    std::cout << "busy      = " << (int)sr.busy << "\n";
    std::cout << "channel   = " << (int)sr.channel << "\n";

    sr.errorCode = 9;   // out of range for 3 bits (max 7) -- silently truncated!
    std::cout << "errorCode after overflow assign = " << (int)sr.errorCode << "\n"; // 1 (9 mod 8)
    return 0;
}
Expected Output
sizeof(StatusRegister) = 1 byte(s) errorCode = 5 busy = 1 channel = 11 errorCode after overflow assign = 1
🔴
Gotcha: bit field layout is NOT portable The C++ standard leaves bit ordering, padding, and cross-compiler layout of bit fields largely implementation-defined. Two different compilers (or the same compiler with a different byte order target) can lay out the exact same struct differently. For real register maps in production firmware, most embedded codebases prefer explicit masks and shifts (as in section 3) or vendor-supplied header macros over bit fields, precisely because masks give you full, portable control over the exact bit layout.
🧠
Key Takeaways — Bit Manipulation &, |, ^, ~, <<, >> operate independently on each bit with no carrying between positions. SET uses OR with a mask, CLEAR uses AND with an inverted mask, TOGGLE uses XOR, and CHECK uses AND followed by a truthiness test. Multi-bit fields are extracted with "mask, then shift." n & (n-1) == 0 detects powers of two. Bit fields are convenient but not layout-portable — real register-mapping code usually prefers manual masks.

Embedded Systems Basics

Everything in this module builds directly on the bit tricks you just learned. Embedded programming is, at its core, C++ talking directly to physical hardware — no operating system cushioning the interaction, tight memory budgets, and real-world timing deadlines that a desktop application never has to worry about. This is the conceptual foundation that sits underneath every lift controller, sensor node, and IoT device you'll ever work on.

1. Microcontroller vs. Microprocessor

A useful analogy: a microprocessor is like a powerful chef's knife — brilliant at its one job (raw computation) but useless without a fully equipped kitchen (RAM chips, storage, I/O controllers) built around it, the way your desktop CPU needs a motherboard full of supporting chips. A microcontroller is a whole compact kitchen in a single drawer — CPU, RAM, flash storage, and I/O peripherals all built onto one chip, ready to run the moment you plug in power.

2. GPIO — General Purpose Input/Output

A GPIO pin is a physical leg on the chip that software can configure to either read a voltage (input — e.g. "is this button pressed?") or drive a voltage (output — e.g. "turn this LED on"). Each pin's behavior is controlled by writing to specific bits in a handful of hardware registers — this is exactly the bit-masking skill from Module 14 in action.

gpio_conceptual.cppC++
#include <cstdint>

// Simplified stand-in for a memory-mapped GPIO peripheral (see section 7 below).
struct GPIO_TypeDef {
    volatile uint32_t MODER;   // mode register:  00=input 01=output per pin (2 bits/pin)
    volatile uint32_t ODR;     // output data register: 1 bit per pin
    volatile uint32_t IDR;     // input data register:  1 bit per pin (read-only)
};

#define GPIOA ((GPIO_TypeDef*)0x40020000)   // real chips place this at a fixed hardware address
#define LED_PIN 5

void configureLedPin() {
    GPIOA->MODER &= ~(0b11 << (LED_PIN * 2));  // clear the 2 mode bits for pin 5
    GPIOA->MODER |=  (0b01 << (LED_PIN * 2));  // set them to 01 = general-purpose output
}

void ledOn()  { GPIOA->ODR |=  (1 << LED_PIN); }   // drive pin 5 high
void ledOff() { GPIOA->ODR &= ~(1 << LED_PIN); }   // drive pin 5 low

bool buttonPressed() {
    #define BUTTON_PIN 0
    return GPIOA->IDR & (1 << BUTTON_PIN);            // read pin 0's current voltage level
}

Walkthrough: MODER uses 2 bits per pin, so pin 5's bits live at positions 10-11. The line GPIOA->MODER &= ~(0b11 << 10) clears those two bits to 00 without touching any other pin's configuration, then the next line ORs in 01 to select output mode — the same clear-then-set idiom from Module 14, just applied to a 2-bit field instead of a single bit.

3. Interrupts

Polling means constantly asking "has anything happened yet?" in a loop — wasteful, like repeatedly checking your phone every second for a text. An interrupt flips this around: the hardware itself taps the CPU on the shoulder the instant something important happens (a timer expires, a button is pressed, a UART byte arrives), pausing whatever the CPU was doing to run a special function called an ISR (Interrupt Service Routine).

isr_pattern.cppC++
#include <cstdint>

volatile bool buttonEventFlag = false;   // shared between ISR and main loop -- must be volatile

// Naming and exact signature are vendor-specific; this shows the shape every ISR takes.
extern "C" void EXTI0_IRQHandler() {
    // 1. Clear the hardware "pending" bit first, or the interrupt re-fires immediately.
    // 2. Keep this function as SHORT as possible -- no printf, no malloc, no blocking calls.
    buttonEventFlag = true;
}

int main() {
    // ... hardware init, then enable the interrupt ...
    while (true) {
        if (buttonEventFlag) {
            buttonEventFlag = false;
            // do the real, possibly slow work here, OUTSIDE the ISR
        }
    }
}
🔴
The golden rule of ISRs Keep them short. An ISR runs with (often) other interrupts disabled or deferred, so a slow ISR delays every other time-critical event in the system. The standard pattern — set a flag or push to a small queue inside the ISR, then do the actual work in the main loop or a task — exists specifically to keep ISR execution time near-zero.

Priority: real chips support multiple interrupt sources with configurable priority levels, so a higher-priority interrupt (say, a safety-critical overcurrent sensor) can preempt a lower-priority one (say, a UART receive) that's already executing. Getting priority levels wrong is a classic source of embedded bugs — a low-priority ISR can starve a high-priority one if priorities are assigned backwards.

4. Timers and Counters

A hardware timer is a register that automatically increments on every clock tick, entirely independent of your program's logic — like a metronome ticking in the background no matter what else the CPU is doing. When the count reaches a configured value, it can trigger an interrupt, toggle a pin, or simply be read by software.

timer_concept.cppC++
// Conceptual: configure a timer to interrupt every 1 millisecond
struct Timer {
    volatile uint32_t PSC;   // prescaler: divides the input clock down
    volatile uint32_t ARR;   // auto-reload value: count target before reset/interrupt
    volatile uint32_t CNT;   // current count value
};

void configureMillisecondTick(Timer* tim, uint32_t sysClockHz) {
    tim->PSC = (sysClockHz / 1000000) - 1;   // scale clock down to 1 MHz (1 tick = 1 microsecond)
    tim->ARR = 1000 - 1;                     // 1000 microsecond ticks = 1 millisecond, then reset
    // enabling the timer and its interrupt is chip-specific register configuration
}

This is exactly how firmware measures elapsed time, generates precise delays, produces PWM (Pulse Width Modulation) signals for motor speed control, and drives the periodic "tick" that an RTOS scheduler relies on — all without the CPU ever sitting in a busy-wait loop.

5. ADC and DAC

The real world is analog — temperature, voltage, sound are all continuous signals — but a microcontroller only understands discrete digital numbers. An ADC (Analog-to-Digital Converter) is the translator that samples a voltage and hands your code a number representing it. A DAC (Digital-to-Analog Converter) works in reverse, turning a number back into a real voltage, for example to drive a speaker or an analog gauge.

adc_concept.cppC++
// A 12-bit ADC reports values 0-4095 for an input voltage between 0V and Vref (often 3.3V)
uint16_t rawReading = readAdcChannel(0);            // e.g. returns 2048
float voltage = (rawReading / 4095.0f) * 3.3f;      // convert to a real-world voltage (~1.65V)

The resolution (number of bits) determines precision: an 8-bit ADC only distinguishes 256 voltage levels, while a 12-bit ADC distinguishes 4096 — the difference between a coarse thermometer and a precise one, using the exact same underlying voltage range.

6. UART, SPI, and I2C — Serial Communication Protocols

These three protocols are how a microcontroller talks to sensors, displays, and other chips. They differ in wiring, speed, and how many devices can share the same bus.

protocol_pseudocode.cppC++
// UART -- simple byte-stream, no addressing, both sides must agree on baud rate beforehand
void uartSendByte(uint8_t b) {
    while (!uartTransmitBufferEmpty()) {}   // wait until hardware is ready
    UART->DATA_REGISTER = b;
}

// SPI -- full-duplex, master drives the clock, device selected by pulling its CS pin low
uint8_t spiTransfer(uint8_t out) {
    setChipSelectLow();
    while (!spiBufferEmpty()) {}
    SPI->DATA_REGISTER = out;
    while (!spiTransferComplete()) {}
    uint8_t in = SPI->DATA_REGISTER;        // received byte arrives as the sent byte clocks out
    setChipSelectHigh();
    return in;
}

// I2C -- every device on the shared bus has a unique 7-bit address
void i2cWrite(uint8_t deviceAddress, uint8_t registerAddr, uint8_t value) {
    i2cStart();
    i2cSendByte((deviceAddress << 1) | 0);  // address + write bit
    i2cSendByte(registerAddr);
    i2cSendByte(value);
    i2cStop();
}

The engineering trade-off: UART is simplest but only connects two devices; I2C shares just two wires among many devices at the cost of speed and more complex addressing logic; SPI is the fastest of the three but needs a dedicated chip-select wire per device, so wiring grows with device count.

7. Memory-Mapped I/O and the volatile Keyword

On most microcontrollers, hardware peripherals don't have their own special instruction set — instead, each register (GPIO, timer, UART, ADC...) is simply assigned a fixed memory address, and reading or writing that address reads or writes the actual hardware. This is memory-mapped I/O: the pointer syntax you already know from Module 2 becomes your interface to physical wires.

volatile_example.cppC++
#define STATUS_REGISTER (*(volatile uint32_t*)0x40001000)

void waitForHardwareReady() {
    while ((STATUS_REGISTER & 0x1) == 0) {
        // busy-wait until the hardware sets the ready bit
    }
}
🔴
Why this loop is broken without volatile From the compiler's point of view, nothing inside this loop ever changes STATUS_REGISTER, so an aggressive optimizer is entitled to read it once, decide the condition never changes, and either optimize the loop into an infinite loop or delete it entirely. volatile tells the compiler "this value can change for reasons outside this program's control (hardware), so re-read it from memory every single time, and never cache it in a register or optimize the access away." It says nothing about thread-safety or atomicity — those are separate concerns handled by the tools from Module 8.

8. Watchdog Timers

A watchdog timer is a hardware safety net: a countdown timer that resets the entire microcontroller if it's ever allowed to reach zero. Firmware must periodically "pet" (reset) the watchdog to prove it's still alive and executing correctly. If a bug ever hangs the main loop — an infinite loop, a deadlock, corrupted memory — the firmware stops petting the watchdog, it expires, and the chip automatically reboots rather than staying frozen forever.

watchdog_concept.cppC++
void petWatchdog() { WATCHDOG->RELOAD_REGISTER = WATCHDOG_RESET_KEY; }

int main() {
    initWatchdog(/*timeout_ms=*/500);   // if not pet within 500ms, chip resets
    while (true) {
        doSensorReading();
        doControlLogic();
        petWatchdog();                 // proves the loop completed a full, healthy cycle
    }
}

This is exactly why a lift controller shouldn't rely purely on software error handling — a watchdog is the last line of defense that recovers the system even from bugs nobody anticipated.

9. Real-Time Constraints and RTOS Basics

A "real-time" system isn't necessarily about being fast — it's about being predictable. A hard real-time system (like an elevator's emergency brake logic) must guarantee a response within a fixed deadline every single time; missing that deadline is treated as a system failure, not just a slowdown. A soft real-time system (like video playback) can tolerate occasional missed deadlines with degraded — but not catastrophic — quality.

On simple firmware, a single while(true) "super-loop" handles everything in sequence. As a project grows to juggle many independent, time-sensitive activities — reading sensors, driving a motor, servicing communication — an RTOS (Real-Time Operating System, e.g. FreeRTOS) becomes valuable: it lets you write each activity as its own independent task, and a scheduler decides which task runs when, based on priority and readiness, all within microsecond-level, deterministic scheduling overhead.

rtos_task_concept.cppC++
// Conceptual shape of two FreeRTOS-style tasks running "concurrently" via preemptive scheduling
void SensorTask(void* params) {
    while (true) {
        readSensors();
        vTaskDelay(pdMS_TO_TICKS(10));   // yield the CPU for 10ms; scheduler runs other tasks
    }
}

void MotorControlTask(void* params) {
    while (true) {
        updateMotorSpeed();
        vTaskDelay(pdMS_TO_TICKS(1));    // higher-frequency task -- runs more often
    }
}

int main() {
    xTaskCreate(SensorTask,       "Sensor", 256, nullptr, /*priority=*/1, nullptr);
    xTaskCreate(MotorControlTask, "Motor",  256, nullptr, /*priority=*/3, nullptr); // higher priority
    vTaskStartScheduler();   // hands control over to the RTOS scheduler; never returns
}

Here, MotorControlTask has a higher priority number, so whenever both tasks are ready to run, the scheduler favors the motor task — appropriate, since a delayed motor correction is far more dangerous than a slightly delayed sensor read.

Key Takeaways — Embedded Systems Basics Microcontrollers integrate CPU, memory, and peripherals on one chip for dedicated control tasks. GPIO, timers, ADC/DAC, and communication peripherals are all configured through registers using the bit-masking idioms from Module 14. Interrupts let hardware events preempt the CPU instead of wasting cycles on polling, but ISRs must stay short. Memory-mapped I/O turns pointer dereferences into hardware control, and volatile stops the compiler from optimizing away those hardware-driven changes. Watchdog timers recover a hung system automatically. Real-time constraints are about deadline predictability, not raw speed, and an RTOS provides deterministic, priority-based scheduling once a single super-loop no longer scales.
